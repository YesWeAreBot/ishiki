# 上下文分区与多场景交互架构重构

状态: 已定
日期: 2026-09-23
来源: 上下文分区设计、主心智模式与渲染机制收敛讨论

## 结论

放弃“单心智 = 单 LLM 上下文流”的等价假设，废除基于物理 Focus 的单场景硬隔离、换代状态机与 Notification 伪装复述机制。

重构为**多视窗物理隔离（One Agent Per Scene）+ 场景原生事实存储（复用 yesimagent Session Storage）+ 显式多目标内生刺激（Explicit Multi-target Internal Stimulus）+ 跨场景只读穿透（Read-only JIT Peeking）**的松耦合架构。

---

## 被否定的前提

### 1. “主心智必须在推理层维持同一个单一上下文容器”
- **原假设**：为了维持跨维度的统一因果链与存在感，一个 Profile 下的所有频道与维度必须汇入同一个执行流与 Context。
- **为什么站不住**：
  - **异构频率撕裂**：游戏具身（秒级控制）与直播弹幕（秒级流式）的高频变动，会持续修改上下文快照，导致 IM 社交等低频频道的 Prompt 前缀缓存彻底归零。
  - **并发阻塞**：单执行流导致多群并发时请求只能串行排队。一个群的多 Step 工具思考会直接挂起并阻塞其余所有频道的即时响应。
- **推翻依据**：存在本体（Identity & Memory）的统一不等于推理视窗（Inference Context）的单一体。人类在游戏挖矿的同时回复微信，工作记忆中加载的是提炼后的高层意图，而非底层秒级传感器与渲染数据。

### 2. “Focus 应该作为控制帧重建与历史可见性的物理硬边界”
- **原假设**：通过声明“一代只读一个场景”，将焦点外的事件阻断在视窗外，依靠 `switch_focus` 在 step 边界换代重建物化帧，以此兼顾专注度与前缀缓存。
- **为什么站不住**：
  - **缓存与焦点高频震荡互斥**：社交群聊节奏不可控。跨群互动导致焦点频繁切换，进而触发物化帧频繁重算，直接击穿四段式赖以生存的前缀缓存。
  - **代偿逻辑变形**：为了让场外点到心智的消息可见，系统不得不发明 `Notification` 机制，将场外事实伪装成当前场景地址写入事实流，严重污染了中性事实。
- **推翻依据**：专注度应由“触发当次唤醒的事件来源”天然界定，不需要在跨 Turn 维度维护一个笨重的进出房间状态机。

### 3. “跨维度自发行为在隔离模型下必然造成因果断裂”
- **原假设**：若维度隔离，游戏取得成就（如挖到钻石）若想在群聊发消息，群聊因缺少前置刺激而在逻辑上产生“自我迷惑”，必须把游戏历史塞入群聊才能解决。
- **为什么站不住**：v3/v4 的困惑根源在于系统把唤醒刺激狭隘地绑定为“外部用户发来了一条消息”。
- **推翻依据**：自发表达的因果起点是实体的“内心冲动”。由源场景向目标场景投递带动机的内生刺激（Internal Stimulus），并在目标视窗发起一次包含因果前因的完整推理，即可在本地形成完美的因果闭环。

### 4. “事实存储必须与 yesimagent 会话存储彻底分离”
- **原假设**：会话文件等同于模型可见台词本，因此必须在外部另建独立的中性事实数据库（Fact Store），以防会话污染事实。
- **为什么站不住**：yesimagent 底层落盘的 `AgentStorage`（`messages.jsonl`）本身就是时序、不可篡改的 `AgentEntry`（原生事实流）；而送入模型的 `ModelMessage[]` 本就是内存中即用即弃的投影。
- **推翻依据**：此前产生“事实被污染”的唯一根源是单心智把多场景混入同一个 JSONL 导致需要 Notification 遮盖。一旦场景物理隔离，每个场景的 `messages.jsonl` 就是该场景最纯净、无损的专属事实流，无需额外引入双层存储开销。

## 新机制

```text
┌─────────────────────────────────────────────────────────────┐
│                          Profile                            │
│  ┌─────────────────────────┐   ┌─────────────────────────┐  │
│  │   Scene A (Group Chat)  │   │     Scene X (Game)      │  │
│  │  - AgentRuntime A       │   │  - AgentRuntime X       │  │
│  │  - messages.jsonl (A)   │   │  - messages.jsonl (X)   │  │
│  │  - Prefix Cache ~100%   │   │  - Independent Loop     │  │
│  └───────────▲─────────────┘   └────────────┬────────────┘  │
│              │                              │               │
│              │ 显式投递 inner_stimulus       │ 成就达成      │
│              │ targets: ["Scene_A"]         │ 触发决策      │
│              └──────────────────────────────┘               │
│                                                             │
│   跨场景只读穿透 (JIT Peeking Tool / Runtime Read-Only Hook)   │
│   Scene A ──(按需查询前情)──> Scene B 的 AgentStorage 局部摘要  │
└─────────────────────────────────────────────────────────────┘
```

### 1. 场景物理隔离（One Agent Per Scene）
- 每个场景（群聊、私聊、游戏、直播）拥有独立的 `AgentRuntime` 实例与独立的 `AgentStorage`（`messages.jsonl`）。
- 每个场景独立维护 Append-only 历史，不与其他场景交织。
- 各场景的 System Prompt 与历史前缀天然冻结，**Prompt 缓存命中率趋近 100%**。
- 并发请求被天然分散到各自独立的执行流，解开横向扩展与吞吐量瓶颈。

### 2. 内生刺激驱动跨场景自发行为（Internal Stimulus Loop）
- 当某一场景产生需要跨场景广播的事件（如游戏挖到钻石）时，由该场景的模型或规则显式声明投递目标：
  `dispatch_stimulus({ targets: ["group_a", "group_b"], reason: "挖到稀有钻石", content: "..." })`
- 目标场景的 AgentRuntime 接收该事件，作为自定义 entry（`type: "inner_stimulus"`）追加到自身的物理事实流中。
- 目标场景触发一次本地完整推理：模型基于本地上下文自主权衡是“插话”还是“保持沉默”，以及如何组织语言，因果链在本地自然闭合。

### 3. 跨场景只读穿透（Read-only JIT Peeking）
- 私聊需要了解群聊前情（例如用户私聊质问“刚才在群里为什么针对我”）时，视窗不常驻群聊历史，也不做全量背景平铺。
- 赋予 Agent 只读查询工具（例如 `peek_channel_history`），或由运行时在确认强相关时以 JIT 形式在 Prompt 尾部临时挂载对应频道的近期事实摘要。
- 严格保持只读，不向目标频道的物理存储写入任何记录，也不破坏本地的稳定前缀缓存。

## 已定细节

1. **投递目标必须显式指定**：跨场景内生刺激禁止使用黑盒规则或模糊推导进行隐式广播，必须由调用方显式给出 `targets` 数组，支持一对一和一对多投递。
2. **完整推理决策权**：接收到内生刺激的目标场景必须走一次完整模型推理（哪怕最终决策是沉默不发），确保语言组织与时机把握由具备本地语境的模型判定。
3. **存储模型对齐**：全面复用 yesimagent 原生 `AgentStorage`，会话日志即客观事实，取消独立的外部 Fact Store。
4. **移除 Focus 物理属性**：Focus 概念不再作为上下文分区分段的边界，不再存在“切换 Focus 触发物化帧换代”的状态机。

随着本重构方案的确立，`packages/koishi-plugin-ishiki/docs/cookbook/` 下的既有设计文档发生大范围失效，具体划界如下：

| 文档 | 失效内容 | 保留/仍有效内容 |
|---|---|---|
| **01-profile.md** | “一个 profile 拥有一个当前场景”；“场景位置属于上下文代际，由检查点携带”等单焦点假设。 | Profile 概念定义；身体（`sid = platform:selfId`）与场景命名空间；白名单过滤与分发边界机制。 |
| **02-attention.md** | **整篇核心机制废弃**：<br>- “心智同一时刻只打开一个场景”；<br>- `Focus` 及其换代机制；<br>- `Notification` 场外事件复述机制；<br>- 可见性与唤醒的单流代偿矩阵。 | 单场景无需跨场景寻址的概念；`send_message` 的基础出站语义。 |
| **03-context.md** | **大幅失效**：<br>- 帧按场景分段与换代重建；<br>- Focus 改变作为检查点触发条件；<br>- 检查点携带 focus 的单代投影逻辑。 | 稳定区、状态、工作区的基本前缀缓存分层思路（在单场景独立视窗内部依然适用）；工具调用配对等连续性不变式。 |
| **04-rendering.md** | - `notification` 共享同一流并按 focus 场景投影的机制；<br>- “一代只读一个场景”的投影约束；<br>- 场外事实通过复述包装进入当前流的逻辑。 | 事实的客观持久性定义；平台事件入口归一化原则；工具轨迹配对原样保留原则。 |
| **README.md** | 涉及 Focus、Notification、单心智多场景切换的核心设计概述。 | Profile 基础架构、无平台分支的整体原则。 |

## 待验证假设

1. **跨场景前情感知的触发策略**：
   - *假设内容*：私聊中感知群聊前情，依靠“带强约束提示词的模型自主调取只读工具”比“运行时基于规则在 Prompt 尾部自动注入”更具灵活性且不易引入幻觉。
   - *验证方法*：对比两者在多轮长对话下的首字延迟、Token 消耗以及模型遗漏检索直接瞎编的概率。
   - *失败意味着*：若弱模型频繁漏检，必须由运行时提供基于规则（如匹配发言人 ID + 时间窗口）的 Prompt 尾部兜底自动挂载机制。

2. **多目标内生刺激并发风暴**：
   - *假设内容*：单次内生事件向 5+ 个活跃群聊并发投递时，不会引发全系统模型推理并发洪峰或 API 速率限制。
   - *验证方法*：在多群模拟高频游戏成就广播，观察各群并发推理的时延与消费表现。
   - *失败意味着*：需要在跨 Agent 刺激投递通道前加装节流阀（Rate Limiter / Priority Queue）。
