# 02 · 唤醒与跨场景

## 一个场景一个心智

每个场景有自己的 agent 和自己的事实流。在这个场景里醒来时，看到的只有这个场景最近的记录。

这条设计的代价是"你在这边不知道那边发生了什么"，而它换来三件事：

- 每个场景的前缀天然冻结，前缀缓存命中率趋近 100%；
- 并发请求分散在各场景自己的执行流里，一个群的深思不会挂起另一个群的回应；
- 没有"场外事件伪装成当前场景"这类代偿逻辑，事实流保持中性。

## 唤醒

一次事实到达时，独立问一个问题：它唤醒这个场景吗？

判断是一组规则：私聊、引用自己的话、命中关键词、提及自己的账号，命中任意一条即唤醒。规则只读，不写任何东西。

结论是 `wait` 时，事实照样落进它所属场景的流里，只是不挂载 agent、不调用模型。场景的历史因此始终完整。

## 单场景的声带

`send_message` 没有目标参数：它只发到当前场景。这不是省略，而是架构约束——在别处凭空出现一句话，那边的你面对一段自己没有的上下文，也绕过那边的语气设定。

想跨场景说话，只有两扇门：

- **只读穿透**：`peek_channel_history` 按地址读取另一个场景的近期事实行。它不挂载对方、不写入对方、不叫醒对方。局限是它只给"发生了什么"，不给对方当下的语气与意图。
- **内生刺激**：`dispatch_stimulus` 把动机和内容一起递过去，落进目标场景自己的事实流，目标场景因此跑一轮完整推理——它可以开口，也可以判断此刻不该说话。

递纸条而不是代对方说话，因果链就在目标场景本地闭合：那边看到的是"别处的我为什么想让我说这句话"，而不是一句从天而降的台词。

## 内生刺激的形态

刺激是一条普通的事实记录，类型 `ishiki.inner_stimulus`，地址属于接收它的场景，载荷里带着：

- `source`：纸条来自哪个场景；
- `reason`：那边的你为什么想说；
- `content`：想让这边知道的事。

它和别的消息一样进入接收方的近期记录，渲染成 `<stimulus …>…</stimulus>` 一行。
刺激之间不建立会话，收到之后怎么处理完全由接收方自己决定。

## 接收方的场景类型

投递的目标只给出地址（`sid` 与 `channelId`）。场景类型用规则自己声明的 `type`；规则没声明时记为 `group`。它不参与规则匹配。

## 投递语义

- 目标必须显式写全（`targets` 数组），一对多可以一次投递；
- 目标必须在自己的白名单内，否则被拒绝并列在工具结果里；
- 投递是异步的：源场景拿到"已送达"就继续自己的回合，不等对方那一轮跑完；
- 不能把纸条投给自己——想给自己留记录，直接做就行。

宿主插件也可以通过服务层的 `emitStimulus` 投递，`trigger: false` 表示只记录、不叫醒对方。
