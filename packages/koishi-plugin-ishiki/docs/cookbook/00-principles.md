# 00 · 原则与被否决的前提

这份 cookbook 描述 ishiki 现在怎么运作。本文件是它的地基：先说清为什么是这样，再说它怎么跑。

每条都记「否决了什么、为什么否决」。想改机制，先读这里；这里的原则被推翻时，改动范围通常不止一个文件。

---

## 1. 存在本体的统一 ≠ 推理视窗的统一

一个 profile 是一个心智，但**不是一个 LLM 上下文**。每个频道有自己的 agent、自己的事实流、自己的模型前缀。

否决的是「同一 profile 的所有频道与维度必须汇入同一个执行流与 Context」。两条理由：

- **异构频率撕裂**：高频维度（游戏控制、直播弹幕）每轮都改上下文快照，低频维度（IM 社交）的前缀缓存会被持续清零。
- **并发阻塞**：单执行流下，一个群的多步工具思考会挂起其余所有频道的即时响应。

人类在打游戏时回微信，工作记忆里加载的是提炼后的高层意图，不是底层传感器数据。存在感由记忆与人格维持，不需要靠共用上下文维持。

默认形态下代价被明确接受：这边不知道那边发生了什么。需要共享语境的场合由配置者显式声明：preset 挂 `cross: true` + `claims` 自行成为一个生效单位，把要合流的频道收进同一块视窗（见 [01-profile](./01-profile.md)）。合流范围写在声明处，不靠工具调用在运行时摸索。

否决的是「靠模型自觉调用工具去别的场景取信息」这条路。实测里模型缺乏「我需要去看别处」的自知之明，工具调用率极低，见 `../../docs/02-cross-channel-preset-architecture.md` 的推翻记录。

## 2. 会话日志即事实

每个场景的 `events.jsonl` 就是该场景的客观事实流：追加写入、时序不变、无第二份真相。模型每轮看到的 `ModelMessage[]` 是内存里即用即弃的投影。

否决的是「事实存储与会话存储分离」，即另建一层 Fact Store。理由：上一代之所以需要伪装的复述（把场外事实改写成当前场景地址再写入），根因是单心智把多场景混进同一个 JSONL；场景物理隔离后，这条需求自动消失。双层存储只会带来双写一致性问题。

推论：投影**不回写**。压缩水位是唯一的例外，它以 `ishiki.compact` 条目追加回事实流（见 [03-context](./03-context.md)）。

## 3. 没有自主心跳

场景实例内部没有常驻定时器。轮次只在有事件落到它头上时开始。

否决的是「每个群维持心跳循环做自主反思与主动说话」。理由：接上百个群会让内存与轮询消耗失控，并且容易在无人群里自言自语。

注意：「没有心跳」不等于「不会主动」。在聚合视窗里，主动发言的判定就发生在被唤醒后的那一轮本地推理里：同一条事实流里别处的发言本身就是「刚才那边发生了什么」的答案，不需要额外的投递通道。

## 4. 声带只属于本地场景

`send_message` 在普通形态下没有目标参数，只发到当前场景；聚合形态下带一个 `target`，坐标必须落在本视窗认领的频道集合内。

否决的是「不打招呼就能往任意外部频道发消息」。理由：接收方的视窗会凭空出现一句自己没说过的话，用户追问时它没有任何前置语境。聚合形态的解法是让这些频道共用同一块视窗——它们看得到彼此说过什么，坐标校验也只在本视窗内开放。

## 5. 引擎管决策，插件管贡献

agent 循环里每个「只能有一个」的环节由**引擎**承担：上下文组装、唤醒判定、工具调用协议。同族引擎互斥，preset 只能选一个。**插件只做加法**：加工具、加提示词。

这是为了根治上一代的扩展模型：插件通过 `priority` 与 `match(session)` 全局抢唤醒拦截权，彼此不兼容、无法组合。只要还有一个插件能挂装配钩子，打架就没根治。

## 6. 显式优于推导

- 合流范围必须写在配置里（`cross: true` + `claims`），不靠模型在运行时决定要不要去看别处。
- 场景与 preset 的绑定写在配置里，不靠规则猜。
- `sid` 是不透明字符串（`platform:selfId`）：只做相等比较，**不反推** platform 与 selfId。地址由受体归一化后随事实一起走。
- 渠道匹配用显式模式（`*` / 前缀 / 精确），不用平台约定反推场景类型。

## 7. 不做检查点状态机

否决了 checkpoint 换代、`state_delta` 旁路记录、侧车 `state.json`。理由：双写一致性与原地篡改的不可审计性，都是自造机制的税；历史修剪用通用的 `compact` 就够了。

好感度、成员画像这类复合状态一律推迟，不提前污染事实流。

## 8. 工具与提示词扩展不占内核机制

工具清单与提示词追加属于插件层，不进内核。内核只保证一件事：场景知道自己在哪，工具自己知道该往哪发。

同理，`AgentPlugin` 必须显式声明；系统级能力由宿主全局注册，不由配置动态决定插件生命周期——Koishi 基于 cordis v3，没有作用域级的插件隔离，硬造一套微型容器只会得到笨重且易错的状态机。

## 9. 平台差异只在受体里归一化

进门的 `Session` 被归一化成中性事实后，场景判断、唤醒判断、渲染都不再有平台分支。平台特有的判据（元素语法、撤回事件、引用结构）只出现在受体与渲染规则里。

## 10. 提示词承载下限，配置只做补充

内置提示词与判据负责写出够用的默认行为，用户的 `instruction` 只在其上追加约束。写得好的 instruction 是加分；写漏了也不该塌掉下限。

## 11. 场景之间没有工具可用的通道

2026-09-27 决定：删掉 `peek_channel_history` 与 `dispatch_stimulus`，连带 `ishiki.inner_stimulus` 事件类型、两条渲染规则、实例上的 `sid` / `address` 字段与 `deliver` 的强制唤醒参数。

理由：这两扇门是为跨推理窗口的上下文物理隔离造的，而 `cross` 形态已经在配置层解决了同一问题——需要共享的频道共用一块视窗，不需要模型在运行时自己决定要不要去看别处。留着它们只会让模型面对一组调用率极低、且一旦调错就写出矛盾事实的工具。

未来方向：**内生刺激会以「agent 之间互相交流」的形式重新引入**，不是恢复这两个工具。重新引入时的形态是 agent 级别的通信，而不是工具级别的窥视与投递；那时单独设计，不把它当这次删掉的补偿。

## 12. 尚未落地与推迟项

这些方向被认可但有意推迟，落地时不要当新设计来讨论：

- **MemoryEngine**：插槽关系已定（它是数据源，不是管道兄弟），实现是空壳，见 [05-engines](./05-engines.md)。
- **投递合批**：消息到达后等一个安静窗口再成批投递给心智，让模型看到完整片段而非碎片。当前由 `join` 隐式聚合兜底。
- **事件用 tool frame 而不是 user message**：语义上更准（外界发生的事 vs 系统对心智说话），需要核心支持工具轨迹式的自定义条目。
- **免打扰闸门（DeliveryGate）**：per-channel 静音，事件照常落盘但不唤醒。
- **穿透规则外化**：把「什么消息值得唤醒」从代码里的规则提到 profile 可配置。
- **可观测性**：工具调用日志已有一部分（`tool.done` / `turn.step` 记耗时与用量），查询与面板未做。
