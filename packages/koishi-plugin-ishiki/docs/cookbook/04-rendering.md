# 04 · 事实、投影与扩展

## 事实

事实是事件进入 profile 后的中性、持久记录。它描述发生了什么，以及发生在哪个场景；不记录：

- 是否唤醒心智；
- 是否成功送达；
- 已经渲染好的正文。

事实携带摄入时可确认的地址（账号与频道）、发送者、消息 ID、时间与必要的引用信息。地址就在事实自己的载荷上，所以「这条事实属于哪里」是读字段而不是逐类型的规则。名称是快照，不由全局实体表回查。

事实流是唯一长期来源，模型看到的近期记录是投影，不回写成第二份事实（压缩水位除外，见 [03-context](./03-context.md) 的 `ishiki.compact`）。

## 事件路径

```text
平台会话
  → 受体归一化为一条事实（平台差异只在这里出现）
  → 规则判断它属于哪个场景（不属于就丢弃）
  → 唤醒引擎判断是否开始一轮
  → 挂载场景实例；事实写进该场景的 events.jsonl
  → 投影：这个场景尾部的事实成为模型读到的消息行
```

内容以平台元素语法原样进入事实；需要读内容的判断（是否被 @、是否命中关键词）读的就是这一段原文。

账号自己的平台消息（`userId === selfId`）在入口丢弃，不进入任何事实流。心智说过的话以工具调用轨迹的形式留在流里，不额外写一条消息行。

## 单事件渲染

渲染规则回答一件事：这个类型怎么读。现在的两条：

| 类型                     | 渲染出的行                                      |
| ------------------------ | ----------------------------------------------- |
| `ishiki.message.created` | `[MM-DD HH:mm] 名字(id) #messageId: 正文`       |
| `ishiki.message.deleted` | `[MM-DD HH:mm] 作者的消息 #id 被 操作者 撤回了` |

未知事件类型采用 fail-closed：可以保存，但不进入模型上下文。

`standard` 引擎把相邻的这些行合并成一条 user 消息（`collapse`），其余角色（user / assistant / tool）原样保留。`classic` 引擎不合并，而是把整个窗口渲染进一条 `<world_state>` 消息。

### 寻址头

`standard` 引擎的聚合视窗在每段开头带一个坐标头 `[#平台:账号/频道]`。头只有坐标，没有作者——每条正文行已经自带作者，头里再写一遍只是把窗口撑大。续段的判据是**频道**：同一频道的连续行合成一段，换人说活不换段，换频道才另起一段。

### 撤回

撤回事件平台只给 id（OneBot 的 `user_id` 是被撤回消息的作者，`operator_id` 是执行撤回的人），昵称靠窗口内见过的人名还原，还原不出就退回裸 id。**是不是自己撤回按 id 判，不按显示名**——同一个人两个昵称时会被误并成一句。两端同一人时合并成一句，避免「X 的消息被 X 撤回」这种卡带读法：

```text
[09-28 00:18] 阿元(17980)撤回了自己的一条消息 #12345
[09-28 00:07] 小林(24456)的消息 #67890 被 管理员(10000) 撤回了
[09-28 00:07] 有一条消息 #67890 被撤回了        ← 平台没给操作者
```

## 工具轨迹

工具调用和结果是心智行为的一部分：

- 在近期记录里保持原顺序和配对；
- 不被任何包装改写；
- 不靠渲染层重新猜测成功或失败：失败就是工具返回的结果里写着失败（例如 `send_message` 的 `{ok: false, error, sent, failedAt}`）。

## 自己的消息

心智说过的话不以消息行存在：它留在流里的是这一轮的 assistant 工具调用与对应的结果。`ishiki.message.created` 只记录外部消息，账号自己的平台回声在入口就被丢弃。

`send_message` 发送失败不生成成功记录；平台没有返回消息 ID 时记一条告警，也不伪造事实。

## 扩展点现状

**引擎族与工具可扩展，受体与渲染规则不可。** 引擎变体走 provider Service（见 [05-engines](./05-engines.md)），新工具经扩展包挂上；但渲染规则与受体归一化仍在包内，新增一种行为意味着改这个包里的代码：

| 想扩展什么       | 现在怎么做                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------ |
| 一种上下文策略   | 继承 `ContextEngine` 提供一个 Koishi 服务，见 [05-engines](./05-engines.md)                                        |
| 一种唤醒判定     | 继承 `WakeupEngine` 提供一个 Koishi 服务                                                                           |
| 一种工具调用协议 | 继承 `ToolcallEngine` 提供一个 Koishi 服务                                                                         |
| 新工具           | 扩展包经 `ctx.ishiki.provide()` 挂到某个 preset，在 `AgentRuntime` 构造期经 `addTools()` 加进工具面                |
| 一种新事件类型   | 在受体（`src/session-handler.ts`）里归一化，在渲染规则（`src/context/standard.engine.ts` 的 `renderLine`）里加一条 |

事件渲染目前由上下文引擎自己做（`standard` 折行合并，`classic` 渲染成 `<world_state>`），没有独立的 renderer 服务，也不承诺这样一条注册机制。`ctx.ishiki` 不提供 `registerReceptor` / `registerTransform` 这类钩子：等第二种受体或第二种渲染策略真的出现时再说——现在加只会得到只有一个实现、无人实现的接口。

## 不做的

- 不引入独立的 state-delta 机制；因果变化由工具结果表达。
- 不依赖 LLM 摘要维持连续性；连续性由事实流与压缩水位提供。
- 不把能力绑定到「当前窗口」这类隐式状态：能力按场景解析，工具自己知道自己站在哪里。
- 复合状态（好感度、成员画像等）推迟，不提前污染事实流。
