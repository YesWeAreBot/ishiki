# koishi-plugin-ishiki 设计规格

> 状态:机制层共识已定(2026-09-19,见 [`mechanism.md`](./mechanism.md)),本文是**行为规格**——段与节奏、可见性、唤醒、寻址、工具、不变式。与 `mechanism.md` 冲突处以 `mechanism.md` 为准;本次重写相对旧版的差异见 §15,代码落点见 [`implementation.md`](./implementation.md)。
>
> 底座:`@yesimagent/core`(entry / turn / storage / plugin hooks)。`athena-harness/docs/cookbook/01-04` 是 athena 的产物,只作「主心智 / 三区 / 平滑过渡」的**模型参考**,不是本插件的既定设计——ishiki 的 agent loop 与存储都用 `@yesimagent/core`,与 athena 的 cortex / nerve / body 无关。

---

## 1. 定位与边界

- ishiki 是 Koishi 插件,目标 = 四段上下文 + 主心智模式。
- 不沿用 athena 的 cortex / nerve / body 设计。
- **一个 profile = 一个主心智 = 一个 `Agent` 实例。**

## 2. Profile

- 以 `profiles.yaml` 声明(数据目录下,不进 Koishi Schema、不上配置页):

  ```yaml
  profiles:
    - id: "boki" # = 心智标识 = Agent id = 数据目录名
      dataPath: "data/ishiki/boki"
      model: "deepseek:deepseek-flash"
      # compactionModel: "..."                 # 可选;缺省用 model
      keywords: ["发布", "上线", "NekoChan"] # 关键词规则(策略,不落盘)
      allowedChannels: # 身体 → 该身体允许的频道(**身体集合的唯一来源**)
        - sid: onebot:1434974784
          channels: [channelA, channelB, "private:*", "!private:12345678"]
        - sid: onebot:12345678
          channels: [channelC]
        - sid: qq:4138444372060156334
          channels: ["private:*"]
  ```

- **没有 `bots` 字段**:一具身体的存在 ⇔ 它在 `allowedChannels` 里有条目(且至少一个频道)。`bodies` 是 `allowedChannels` 里出现过的 sid 集合——派生量不重复声明,避免两处需要保持同步。
  - 附带校验:`allowedChannels` 里的 sid 若在 `ctx.bots` 里找不到(适配器还没连上或拼错),`ready` 时打 `WARN`(不抛错——适配器可能稍后才连)。
- `allowedChannels` **同时是身体归属与频道白名单**:身体决定这具 bot 账号是否归这个心智,频道决定它是否被允许在那里运行。两者都成立才接管,**可见 = 可响应**。
- **隔离**:不同 profile 之间完全隔离,即使共用同一个 bot 账号。名字也不共享——昵称与频道名随事实一起快照(§3),一个 profile 里的改名不会改写另一个 profile 的历史。
- **摄入过滤**:`身体 ∈ allowedChannels 的 sid 集合` ∧ `频道在该身体的白名单内` ∧ `发送者 ∉ 该 sid 集合`。发送者是自己任何一具身体 → 直接 skip,不入 storage。
  - 推论:自己在本 focus 的动作由内核的 assistant / tool 条目承担,不靠 session 摄入;同一句发言不会在流里出现两次。
- **「两具身体落在同一个群」被配置层拒绝**(加载期抛错,见 implementation.md 的『加载期静态校验』),所以不需要去重:跨平台(如一路 OneBot 民间协议、一路官方 QQ Bot)时 `messageId` 与 `userId` 的命名空间都不同,去重的输入本身不成立,只能在配置层拒绝;而这条路也判不出来(命名空间不可比)。
- **外部 bot 就是普通用户**:不查名单、不识别、不抑制。
- **加载期静态校验**(三条,细节见 implementation.md 的『加载期静态校验』):① 同 profile 内、同一平台下两具身体的**多方场景**(群/频道)集合不相交——两方场景(`private:*`)**豁免**,因为 `private:U` 在两具身体下是两段不同的对话;② 跨 profile 同一 sid 的**全部**场景集合不相交(此处两方场景也校验——它管的是所有权划分,不是重复投递);③ 不同平台的频道 id 不比较。失败 → 抛错,拒绝启动。
  - 频道规则的语义:`kind:exact`(精确)、`kind:*`(该 kind 的全部)、`!` 前缀为排除项。例如 `private:*` + `!private:A` 表示「除 A 以外的所有私聊」,于是共用同一 bot 账号的另一 profile 只能用 `private:A`。
  - 判定可算:kind 相同的 `*` 之间做补集运算,`*` 与 `exact` 之间做成员判定,kind 不同的天然不相交——不需要枚举运行期频道。
  - 零命中(没有任何 profile 接管某条 session)→ 静默忽略(不摄入、不响应)。
- **关键词规则**:`profiles.yaml` 每 profile 一段 `keywords`(与 `allowedChannels` 同级)。判定面 = `session.content`(渲染后的文本,即最终投影进上下文的同一份文本),不读平台原始的 `raw_message`——那要理解 CQ 码之类的平台格式,与「核心不硬编码平台细节」冲突。关键词属**策略**,不写进事实、不落盘。

## 3. 摄入层:事实(facts)

- `session → ishiki event`:每种 session 类型一个 projector,负责解析并填好**事实**。
- 事实**不含策略**:不写「这是不是 awareness」、不写「要不要渲染」。
- 声明为 `AgentCustomMessage`(`ishiki.message.created` / `ishiki.message.deleted`;同处还声明了心智自有的 `ishiki.self.message` 与 `ishiki.inner.thought`)。同一条对象既是**档案记录**也是 **turn 触发消息**(不触发时用 `send(message, { trigger: false })`)。
- **场景身份 = 身体 + 频道**:`Scene = (platform, selfId, channelId)`。`channelId` 的语义域是 `selfId`——同一平台下不同身体的频道 id 可比,跨平台不可比,所以身体必须留在身份里。
- 事件同样摄入;事件可作 event 型 awareness(poke / 撤回 / 成员变动…)。`login-*` 描述的是自己身体的状态,归档案 / state,不作 awareness。
- **事实字段(v1 范围)**:`quote` 只存 `{ id, content }`,不补被引消息的发送者;**不新增 `mentions` 字段**——被 @ 的信息按需从 `content` 解析(判定层只读 `content` + `selfId`)。
  - **平台差异在 projector 里归一化**:onebot 的 `message-created` 里 @ 是元素形式(`content` 内含 `<at id="…"/>`);QQ 的群聊 @ 走**独立 session 类型**(`type=internal`、`_type=qq/group-at-message-create`,其 `_data` 里没有提升出来的 channel / message,需要读平台字段),projector 必须把这一信号归一化进 `content`——否则它彻底丢失。
  - 于是判定层不需要平台分支:`atSelf` = `content` 里出现指向本 profile 任一身体(= `allowedChannels` 的 sid 集合)的 at 标记。`quote` 的发送者判定仍然没有输入(§14)。
- 未知 session 类型:只档案,不渲染(fail-closed)。
- **名字随事实快照,不设全局实体表**:事实里带 `user: { id, name? }` 与 `channel: { id, name?, direct }`,取摄入那一刻 `session.author?.name` 与 `session.event?.channel?.name`。
  - 前缀稳定是白送的:改名只影响此后新摄入的事实,旧行永远是当时看到的名字,不需要渲染期解析这一步。
  - 代价是重复(同一个频道名在每行事实里各存一份)且没有追溯回填——改名不修正历史,也不打算修正。
  - 缺名回退到 id(fail-soft)。

## 4. 四段布局

```
[稳定区]   persona / 规则 / 工具 schema / 身体与频道清单   不变,逐字节稳定
[帧·历史]  <memory> + <history>                           检查点节奏,冻结
[状态槽]   <state> 当前时间 / …                            turn 节奏,重渲染
[工作区]   新消息、工具轨迹、awareness                      append-only
```

- **分段的理由不是「分成几块」**:前缀缓存按字节匹配,任何「每 turn 可能变的信息」只有三条路——追加、原地替换、等检查点,没有第四条(机制论证见 `mechanism.md` §1)。分段的真正价值是把信息**按性质分流到不同路线**。
- **历史段是缓存的经济单位**(必须低频重算),**状态部分是新鲜度的单位**(应该高频)——两者不能绑死在同一个节奏上。把状态槽从帧里拆出来,就是让这两件事各自有节奏。
- **「变得越慢的越靠前」**仍然成立。
- **稳定区讲的是模式**:一次唤醒是一个 turn、turn 由 step 组成、怎么结束本轮、`finish` 是沉默这个选项、focus 是什么、焦点内的事件是裸行、别处的事件带 `<awareness>` 包装、有没有切过 focus。稳定区里要列出「身体 → 该身体可达的频道」(静态配置派生量,缓存友好);工具的参数与返回值**只写在工具 schema 里**——稳定区再抄一份就会与 schema 漂移。

信息路由表:

| 信息                                       | 节奏                     | 归属                     |
| ------------------------------------------ | ------------------------ | ------------------------ |
| persona、规则、工具 schema、身体与频道清单 | 不变                     | 稳定区                   |
| 关系、承诺、未决事项                       | 慢、需综合               | 帧·`<memory>`(LLM)       |
| 对话近史                                   | 慢、需原文质感           | 帧·`<history>`(机械窗口) |
| 粗时间、话题                               | 每 turn 可能变、小、低熵 | 状态槽(原地替换)         |
| 新消息、工具轨迹、自致行为                 | 事件驱动、需因果         | 工作区(追加)             |
| 多样性 / 情绪 marker                       | 每 turn、自包含          | 工作区追加(latest-wins)  |

## 5. 帧·历史:按场景分组

```
<frame>                     帧头:at / focus_sid / focus_channel [name]
<memory>                    慢层:LLM 综合的承诺 / 关系 / 未决(预算内,"据回忆"性质)
<history sid channel focus> 当前窗口:这一代在它里面发生的事(工作区折叠)
<history sid channel>       这一代工作过的别的场景:各自的切片
<history sid channel>       只被叫到过的场景:存储尾部 N 条 + 时间窗口
```

- **自己的话走普通事实通道。** 模仿风险来自无限持久,而一代的量有界;更硬的理由是对话完整性——hist 里留着「Alice: 你为什么这么说?」而没有我的话,模型面对无因之果,重复风险反而上升。落法:**成功的 `send_message` 落盘一条自己的消息事实**(类型 `ishiki.self.message`,带平台返回的 messageId 与自己的 user 快照),帧里与别人的行同格式渲染(`[HH:MM] 名(id) #msgId: 正文`);发往别的场景的也不例外,它本来就是那个场景的事实,于是落在那个场景的段里。失败不发事实:它只留在工具轨迹里。**`【我:内容】` 与 `<self>` 块已删除**——不再从调用参数里反推内容、寻址与归属。可见性见 §7:进帧,不进工作区。
- **先选择后综合。** 机械窗口是忠实裁剪(丢了什么可知),LLM 摘要是不可信压缩(会错、会丢错东西)。摘要只干慢层;把摘要当历史段主产品,就是拿最不可信的工具干最需要保真的活。
- **没信号的场景不进帧。** 注意力过滤的产物就是遗忘,而「看过没理」没有可操作的判定(没 peek?peek 了没回?),任意的判据驱动持久标记会把过滤器变成任务队列——persist 在冻结帧里偏置最黏。被提起时,「你怎么不理」本身就是恢复路径,peek 补状态。帧里不写任何未处理数或待回列表。
- **`<memory>` 是慢层**,v1 不出现(机械剪枝 + 释放契约已足以定义历史段);它解决的是「压的是意义不是事件」这一类,落地见 §14。

### 5.1 归属规则:块头 = 区段唯一开头

- **帧是唯一块头**:`<frame at="HH:MM" focus_sid="…" focus_channel="…" [name="…"]>`。`<memory>` / `<history>` 是**区段**,不是块头。
- 每个场景区段都有显式开头;区段内裸行属于最近的开头;区段外的东西各有显式包装。模型的判定收敛为一条:**往前找最近的块头 / 包装**。
- 块头只允许三个来源:位置声明(帧 / 投影自给的 `<frame …/>`)、focus change(降级路径,直接渲染成带 `from` / `reason` 属性的块头,不是旁白行)、夹断重开(awareness / 工具轨迹插进段中间后重开)。
- 每个场景的段头自声明 `sid` / `channel`,段内裸行只属于那个场景,跨段引用消失。
- **每行场景短标记否决**:focus 行是消息大头,每行 +8~12 token 是持续成本,而它消除的歧义块头已经消除。仅在块头方案实际观察到误判时再升级。
- switch 立即换代落地后,归属歧义在 happy path 结构性消失;本规则约束**工作区投影**(时序交织 + cursor + 块头)与**降级路径**(checkpoint 写失败、旧流)。

## 6. 状态槽

- **定义**:位于帧·历史与工作区之间的独立段,内容**每 step 从权威状态重新生成**——不冻结、不参与折叠、不落盘(不进 checkpoint payload)。
- **v1 字段**:

```
<state>
当前时间:2026年9月19日 凌晨
</state>
```

- 标签恒为 `<state>`,字段一行 `键:值`;属性只留给不参与内容的元数据。
- **时间取挂钟**,4 档:凌晨(00–05)/ 上午(06–11)/ 下午(12–17)/ 晚上(18–23),带年月日。这是全文**唯一一处「投影读此刻」**的地方——它让「沉默很久之后醒来」时槽说的是「现在」,也收窄了槽的输入(不必先取流)。代价见 §13 不变式 2。
- **变更门控**:状态没变就不重渲染 → 字节不变 → 缓存从帧·历史起照常命中。时间档一天最多变 4 次,满足「档位变更频率远低于检查点间隔」。
- **护栏:槽必须小而低熵。** 槽里任何一个高频字段(未量化的时间、每轮都变的情绪 marker)都会把「50 token 的一次小 miss」变成「每轮重付整个工作区」。规则:**槽里只放慢变量;热字段一律迁去工作区 append 行**——改的是字段去向,不是释放时机。
- **槽即动态注入点**:「像酒馆那样动态注入」走的就是原地替换路线;门控让静态注入零成本。
- **在场者不做(09-19 否决)**:焦点场景每一行都带 `名(id)`,名单是那些行的纯派生;而它是槽里唯一随消息流量变化的字段——一个新面孔 = 从该字节到工作区末尾的全额重付。槽只放慢变量。
- 其余字段(话题 / 注入件)的清单与来源**未定**(§14),按同一护栏逐个评估后加入。
- **focus 不进槽。** 位置声明归帧;立即换代之后帧头永不过时,把 focus 再写一份只会制造「帧说 A、槽说 B」的第二个声明源。这条**依赖立即换代**(§9):若换代退回 turn 边界,帧头在 turn 内就会过时,那时才需要槽兜底。

## 7. 工作区与渲染管线

| 阶段                                    | 输入               | 输出                                         | 契约                                       |
| --------------------------------------- | ------------------ | -------------------------------------------- | ------------------------------------------ |
| `transformEntries(entries, { turnId })` | 全部 entry(含边界) | 原生 `AgentMessage[]`:帧 + 状态槽 + 本代投影 | 只能产出 message 条目,否则活不过内核的过滤 |

- **投影只有一个 hook**:`transformEntries` 是唯一拿得到 entry 的 hook,所以边界、cursor、渲染与包装都在一次遍历里完成——不需要渲染 type,不需要第二个 hook,也不需要在 hook 之间传递投影语境。
- **投影输出原生消息**:帧与状态槽都是 `user` 消息,事实是裸行或 awareness 块的 `user` 消息,assistant / tool / `user` 条目原样通过;不新增渲染 type。
- **帧渲染 = 整帧一条 `user` message**,内部用区段标签分区。语义上帧是「系统给它的状态陈述」,不是主心智自己的口吻——各段因此不需要靠 role 区分,靠段头标签。
- **帧的确切布局**:`<frame at focus_sid focus_channel name>` + [`<memory>`] + 若干 `<history sid channel [focus]>` 段 + `</frame>`。`at` 是帧创建时间(`HH:MM`);`focus_sid` / `focus_channel` / `name` 声明当前 focus,`name` 取该代首条同场景事实的频道名(没有就省略)。带 `focus` 的那段是当前窗口且排最前,其余段按最近活跃倒序。投影自己给的位置声明是同一元素的空壳 `<frame …/>`:取值只用该代首条 entry 的时钟与 initial focus,所以同一 turn 的每一步渲染出同一串。
- **形态判定**:cursor 由帧声明的起点 + 已记录的切换推进;落在 cursor 场景里的事实渲染成裸行,别处**够得着**的事实包一层 `<awareness>`(判定与唤醒同源,所以叫醒本轮的那条事实不会在轮内不可见)。
- **行**:`[HH:MM] 名(userId) #msgId: 正文`(名缺则只写 id);**每行恒带 `msgId`**——`quote id=` 需要它,而「哪条会被引用」无法预知。名随事实快照,缺则只写 id。
- **焦点内的事件不逐条包装**:位置声明已经写明焦点,一段连续的窗口内事件只在开头带一次 `<focus sid channel>` 块头(不闭合),中间夹进别的东西后再出现就重开一段。awareness 块头 = `<awareness sid channel name>`,`name` 缺则省略,**不带触发原因**——模型只需要知道「这条不在焦点里」。
- **awareness 不聚合**:一条事实一个块。同场景连续命中不再合并成一块——合并要求在原地改写已渲染的尾部块,与工作区 append-only、形态一次性冲突;封顶 + `+n` 同样否决,`+n` 本身是每 step 都变的热字段。
- **帧内不重复**:每条事实只有一个归属场景,所以同一段话在帧里只出现一次;心智自己的话也是那个场景的事实,同样只出现一次。帧内没有 `<awareness>` / `<self>` 包装,也就没有把同一段话印第二遍的地方。
- **未理会的 awareness 刻意遗忘,不留残值**;scenes 只载中性内容(§5)。
- **自己的话**:工作区内 `inner_thought` 渲染成心智自己的 `assistant` 消息;assistant 消息(文本 + tool-call)在**本代内原样保留**——tool-call 部分**必须**保留(与 tool result 成对,否则 provider 直接拒);`ishiki.self.message` 事实**不进工作区投影**(§5),工作区里「我说过什么」由那次 `send_message` 的 tool-call 承担。
- **`peek_channel` 的结果自带 `<peek sid channel count>`**:它是回答,不是事件,必须自己声明读的是哪个场景。
- **单场景裁剪与 tier 降级**未实现(§12 / §14)。

## 8. 释放契约与检查点

- **边界** = `ishiki.checkpoint` entry(`AgentCustomEntry` 扩展点)。payload 钉住:`frameFocus`、`prevFocus`、**已渲染的帧文本**、时间戳。
- **不物化**:帧与工作区都由 fold 从 entry 流派生,合成条目不落盘;唯一物化的是**帧文本**——它派生不出来(上一代的条目在被折叠时才获得新的解释),生成一次、之后每个 step 只读这一份。
- **释放管的是轨迹**(`<history>` / 工作区),只在检查点发生。三条触发器**各自独立判定**,同一边界撞上自然合并成一次:

| 触发器              | 动作                                    |
| ------------------- | --------------------------------------- |
| 槽变                | 只换槽,付一次小 miss,工作区原样沿用     |
| 帧变(focus 切换)    | 检查点 + 释放,强制;时机 = step 边界(§9) |
| W 超阈值 / 空闲够久 | 检查点 + 释放                           |

- **「槽变 → 顺带释放工作区」明确否决**:前缀缓存是**最长公共前缀**,不是全有全无。槽变只失效槽字节起的一截、只此一轮;下一轮 `[稳定区][帧·历史][槽'][工作区A][新消息]` 中工作区 A 自动回到缓存——「逐字沿用」不需要任何操作,它就是免费的。释放它 = 本轮多付一次折叠(含 LLM 调用)+ 不可逆保真损失,去换一笔本会自动回本的缓存债;而且检查点之间的工作区是全系统唯一的**原文近史**,释放它就是让 v3 病(每次重建都是有损投影)从后门回来。**判据:「保留 vs 释放」是 W 的函数,不是「是否发生过一次 miss」的函数。**
- **W 的口径**:只算最后一条 `ishiki.checkpoint` 之后的条目(摄入事实、assistant / tool 条目、nudge),字符数 ÷ `charsPerToken`。不计 instructions / persona / 工具 schema(它们不在 entry 流里),不计帧区,不计上一版摘要(它在 payload 里)。一个顺带的性质:这也**间接约束了帧的规模**——帧是上一代工作区的剪枝产物,工作区被阈值卡住,帧就跟着被卡住。
- **工作区代内 append-only**:代内任何修剪都是缓存自杀。
- **归档轮转**(v1 未实现):`messages.jsonl` 超过 `archive.maxKB` 或人工触发时轮转——旧文件移入 `archive/`,新建同路径文件,并在头部写入一条 compact(= 边界 entry:状态快照 + 可选摘要)。归档与重建是**同一种事务**(一次 `append` + 可选 LLM 压缩),同样只在无活动 turn 时发生。
  - 压缩失败 → **机械回退**(不用模型):把上一轮的**帧文本**作为文本快照存进 compact,新文件 = `[compact]` + 当前代条目**原样搬入**——上下文完全不变,只削掉帧之前的历史。该快照不参与运行时渲染,但压缩输入把它当作上一版摘要,所以机械回退 = 叙事压缩延后一代,不是永久丢失。
  - 对齐 YesImBot 的三条既有语义:空会话拒绝归档;有 summary 时新文件以 compact 开头;`no-summary` 是显式选项(用户接受叙事断档)。
- **开机帧**:全新 profile(stream 为空)在**第一次 turn 之前**写一条开局帧,声明初始焦点,并带一句只在这一代成立的话(「在此之前没有发生过任何事」——说的是记录,不是身体状态)。选在第一次 turn 之前而不是首轮结束之后,是因为后者会改写已经发出去的前缀。
- **重启不是触发条件**:帧本来就从 storage 派生;旧流或开局帧写入失败时,投影按同一元素自行给出位置声明。
- **压缩的模型** = `compactionModel ?? profile.model`,输出一段有 token 预算的自由文本,写在边界 entry 的 payload 里落盘。压缩失败或写入失败 → **不写边界**,本代继续,下次触发重试(`onTurnFinish` 会吞异常,重建必须自己 catch + log)。

## 9. 主心智与切换

- **能力全局**:发送能力显式寻址任何时刻可用;focus 只决定**默认寻址** + **哪个场景的历史进缓存帧**。
- **reach ⊇ wake**:起 turn 贵、进工作区可见便宜;叫醒你的事实必须可见,反之不必叫醒。
- **切换经济学**:持续投入一个场景 → switch(一次检查点,历史进帧摊销);顺路回一句 → 不切,显式寻址 + 必要时 peek。频繁横跳的病态用法本就该「不切而发」。
- **switch 采纳「立即换代」**:换代从 turn 边界提前到 **step 边界**,切换在语义和字节上同时完成。
  - **流内转换消失**:工作区不再出现 change 事件;switch 后的消息裸行在帧 B 之后的干净流里,归属 = 帧头,零状态跟踪、零歧义。
  - **帧头永不过时**:不再是「帧说在 A、工作区说在 B」的过时声明。
  - **时机 = step 边界**(内核 `onStepFinish`),不是工具 `execute` 内——那里本 step 的条目还没写完,重建会读到残缺工作区。
  - **切换语义被 checkpoint 吸收**:`frameFocus + prevFocus` 已完整表达一次切换,成功路径不再落独立 change 条目。
  - **change 条目降级为保险丝**:`checkpoint` 写失败时才落最小 change 标记;fold 的流内换挡逻辑保留作降级路径(§5.1)。
  - **慢层延迟保护**:切换重建的 `<memory>` 段延用旧版文本,慢层异步重算、下一检查点替换——memory 是慢层,晚一代无妨。
  - **重启恢复简化**:live focus = 最后 checkpoint 的 `frameFocus`,不再扫描流找 change 条目。
  - **代价与守恒**:缓存账上换代 miss 总量守恒(时机只是搬家——turn 必然结束,帧 A 必然死于换代);语义上**一次换代把本步已经发生的一切留在被离开的那个场景**:工具轨迹按调用发生时的 cursor 归属,所以新焦点段里不会有上一步的调用。新的工作区从换代点开始。
- **代内单切是结构性的,不再有冷却**:一次切换就是一代的结束,所以「一代只切一次」由帧形状(单 `prevFocus` 槽)自动成立,同一 step 里连切 = 连着结束两代。顺路需求由「不切而发」兜底,连切的成本由帧级 miss 自限。冷却(一代只切一次 / `focusSwitch.minIntervalMinutes`)在 v1 **没有实现**,它只是将来可加的成本护栏。
- **awareness 不触发帧重建**;主心智可忽略、`peek_channel` 查看来源、旁路行动或切换 focus。

## 10. scope 降级与寻址

- **场景身份 = 身体 + 频道**(`(platform, selfId, channelId)`)。`channelId` 的语义域是 `selfId`:同一平台下不同身体的频道 id 可比,跨平台不可比,所以身体必须留在身份里。
- 降级维度是两个量:

  | 声明派生的 scope                         | 才存在的东西                                                                                                   |
  | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
  | 单场景(一具身体 + 它只有一个 exact 频道) | 无 `sid`、无 `channel`、无 `switch_focus`、无 `peek_channel`、无 awareness、无 focus 声明;提示词不含主心智叙事 |
  | 身体数 > 1                               | `sid` 参数                                                                                                     |
  | 任一身体频道数 > 1                       | `channel` 参数                                                                                                 |
  | 场景数 > 1(即 `!singleScene`)            | focus 声明、`switch_focus`、`peek_channel`、awareness 判定机制                                                 |
  - 「单场景」按**声明**判定:`private:*` 展开的是家族,即使运行时只遇到一个私聊频道,scope 仍是多场景。
  - 这个公式成立靠一条静态校验:**同平台下同一 profile 的两具身体频道集合必须不相交**。它挡住了「两具身体同频道」这种公式算不对、去重也救不了的形态。

- 降级必须在装配期**同时**落到四处:工具是否提供该参数、description 怎么写、提示词是否提及、**渲染格式是否出现该字段**。四者不同进同退就是 false capability 或幽灵参数。
- **寻址**:`sid` 省略即 logical focus 的身体;`channel` 省略即该身体唯一允许的频道(不唯一则必须显式给,否则结构化错误)。Koishi 的 `channel.id` 是裸 id(样本:onebot `857518324` / qq `BC1E3F68…` / sandbox `@Alice`),所以 `sid` 决定命名空间。
- **可见与可响应**:`allowedChannels` 同时是身体归属与频道白名单——身体决定这具 bot 是否归我,频道决定是否被允许在那里运行;两者都成立才接管,接管即响应。

## 11. 可见性与唤醒

|          | focus 场景的普通条目  | 命中事实的条目(任意场景)                                   |
| -------- | --------------------- | ---------------------------------------------------------- |
| 进上下文 | 是(focus 形态)        | 是(非 focus 时为 awareness 形态)                           |
| 起 turn  | 否(累积,等下一次唤醒) | **是**(空闲时起新 turn;有 turn 在跑时作为 step delta join) |

- 可见性(渲染层)与唤醒(触发层)是**两套谓词**,事实由 projector 提供,策略不写进事实。
- `decide` = 场景相关性(cursor)∧ 事件相关性(事实)。

## 12. 工具

主心智的能力清单只有三项:切换默认情境、旁路读取、感知 awareness(awareness 不是工具)。工具集与它 1:1 对应,另加两个「表达 / 结束」的出口——不多不少。

| 工具           | 存在条件   | 作用                   | 关键点                                                                                                                                                                                          |
| -------------- | ---------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `send_message` | 所有 tier  | 唯一的表达出口         | 省略 `sid` → logical focus 的身体;省略 `channel` → 该身体唯一允许的频道;`messages[]` 多条 = 多气泡(拟人分句);`mode` = element / raw;`continue` 为真则发完继续本 turn,否则结束 turn(step 级决定) |
| `finish`       | 所有 tier  | 显式结束 turn 而不发言 | 让「不回复」成为显式决策(「我看过了 / 我已完成」)                                                                                                                                               |
| `switch_focus` | 场景数 > 1 | 改变默认情境           | 只改 logical focus 并**在 step 边界立即换代**(§9);**成功路径不落 change 条目**;change 条目降级为 checkpoint 写失败的保险丝;连切的成本由帧级 miss 自限,冷却降级为可选护栏                        |
| `peek_channel` | 场景数 > 1 | 不改 focus 的旁路查看  | 结果是 tool result,进当步工作区;不改 focus、不触发重建                                                                                                                                          |

- 平台原生能力(禁言、撤回、精华、表情回应…)不属 v1:由附属插件按 profile 注册、按 tier 门控,走同一套工具注册概念。
- 不把 `send_sticker` / `send_voice` 拆成独立工具:在用户看来都是「发消息」,用 `send_message` 的 element 模式表达。
- 不提供记忆 / 检索类工具:v1 没有长期记忆机制。
- **tier 降级尚未实现**:参数集合目前固定,不随场景数增删;已定的原则不变——**参数不存在时,schema、description 与稳定区同时不含它**。

### 12.1 step 0 未产出工具调用(兜底)

不用 `toolChoice: "required"`——部分模型在思考模式下会以 400 拒绝它。改为**事后校验 + 一次重试**:

- **判据**:turn 结束时检查「本 turn 从未产生工具结果」= step 0 只输出了文本(零工具调用时内核的 `continue` 为 false,turn 直接结束)。
- **重试**:写入一条 nudge(CustomMessage),`send(nudge, { trigger: true })`。内核没有「零调用后继续同一 turn」的路径,所以重试必然是新 turn。
- **必须 `ifBusy: "defer"`**:turn 收尾时队列仍认为该 turn active——`"reject"` 抛 `AgentBusyError` 而插件异常被内核吞掉(静默失败);`"join"` 会把消息塞进正在收尾的 turn(静默丢失);`"defer"` 排队,重试成为下一个 turn。
- **成本低**:重试请求的 instructions + 帧 + 状态槽 + 工作区逐字节不变,nudge 只追加在尾部 → 前缀缓存全命中,只多付 nudge + 输出 token。
- **有界**:最多重试一次;再一次仍无工具调用 → 接受为「不回复」,记 warning。
- **nudge 的可见范围 = 随流保留**:它像普通条目一样经剪枝进入 `<history>`,与「失败的原文必须保留」一致;措辞中性,避免模型模仿自己的失误。
- **排队 nudge 时跳过本次重建**:零工具调用的 turn 不可能发生切换(切换本身是工具调用),而重建会白付一次压缩 LLM 调用。

## 13. 不变式

1. **前缀稳定**:instructions + 帧逐字节不变;变化只发生在边界(重建时整块换)。
2. **投影纯度收窄(09-19)**:除**状态槽**外,投影是 entry 流的纯函数——同一条流两次投影逐字节相同,条目形态由它在流中的位置决定。状态槽取挂钟,是唯一例外,因而不进任何「同流两次投影相同」的断言;复盘「模型当时看到了什么」依赖 `dumpRequests` 的 dump,而不是靠流重放。
3. **边界只在 step / turn 边界写入**(切换 = step 边界;预算 / 空闲 = turn 边界;归档 = `isIdle()`)。「turn 内帧冻结」是结构性的,不靠约定。
4. **可见性没有结构保证**:摄入条目是 CustomMessage,天生走消息路径,因此必须由 fold 显式表态(丢弃 / 改写)。
5. **工具 schema、description、提示词三者同进同退。**
6. **流只增不改**:撤回、编辑、封禁、身体离线等「后续事件否定先前条目」的情况,本代只能以追加表达;真正移除只能在重建时由剪枝完成。
7. **条目只在 step / turn 边界落盘**(内核保证):工具配对不会被渲染块打断,因此折叠层不需要任何缓冲或重排规则——它只按流顺序映射。

| `context.sceneWindowMs`          | `24h`                                              | 落帧:从存储读回来的场景段只收这么久以内的事实                                                                                           |
| `compaction.maxTokens`           | `1000`                                             | 压缩器:摘要输出预算                                                                                                                     |
| `archive.maxKB`                  | `5120`(`0` = 禁用)                                 | 归档检查(turn 结束 / 空闲):当前 `messages.jsonl` 超阈值 → 轮转                                                                          |
| `focusSwitch.minIntervalMinutes` | `0`                                                | 可选成本护栏(不再是正确性约束):上次切换距今多久才允许再切                                                                               |
| `wakeOn`                         | `["direct", "atSelf", "keyword"]`                  | session 处理器:命中才 `trigger: true`                                                                                                   |
| `send.maxBubbles`                | `5`                                                | `send_message` 入参校验:超出返回结构化错误,绝不静默截断                                                                                 |
| `peek.limit` / `peek.maxLimit`   | `20` / `50`                                        | `peek_channel`:默认条数 / 硬上限                                                                                                        |

### 16.3 唤醒谓词的输入

- `direct` → `session.isDirect`(Koishi 访问器)
- `atSelf` → 解析 `content` 里的 at 标记,比对本 profile 的身体集合(§3)。平台差异在 projector 里抹平。**不写入 `mentions` 字段。**
- `keyword` → `profile.keywords` 与 `session.content` 的包含判定

`quote`(「这条在回复我」)不在 v1:`quote` 只存 `{id, content}`,没有发送者。

> 已知平台事实:QQ 群机器人只会把 **@ 它的消息**推给 bot(`qq/group-at-message-create` 是唯一可用的群消息类型),所以「QQ 群里的普通消息」在这个适配器上本来就不存在。
