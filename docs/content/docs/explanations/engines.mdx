Ishiki 把「一次对话中的模型侧行为」拆成三族正交的引擎：上下文（看什么）、唤醒（理不理）、工具调用（怎么做）。本文讲清这个拆分为什么成立、组合如何实现、以及自己写一个引擎意味着什么。

## 为什么是三族

一次群聊交互里，模型侧要回答三个互相独立的问题：

1. **这条消息要不要理？** —— 唤醒引擎（wakeup）
2. **这一轮给模型看什么？** —— 上下文引擎（context）
3. **模型怎么表达「用工具」？** —— 工具调用引擎（toolcall）

这些选择大多可以独立组合：意愿唤醒配 WorldState 上下文、规则唤醒配线性历史、v3 上下文配原生工具调用。每一维都能替换，不必切换整套「预设方案」。

配置上，profile 的三个段（`wakeup`/`context`/`toolcall`）各自带 `engine` 字段与私有参数。`narrative` 是配套合同：它的上下文引擎提供剧本与输入位置标记，工具调用引擎消费这些标记；要用叙事工具调用就必须同时启用叙事上下文，唤醒选择仍独立。narrative 不在主插件里，由独立插件 `koishi-plugin-ishiki-narrative` 提供。

## 组合机制：Koishi Service

每个引擎是一个 Koishi Service，按约定名字注册：`ishiki.engine.context.standard`、`ishiki.engine.wakeup.jev`……主插件启动时注册全部内置引擎；第三方引擎作为普通 Koishi 插件安装即可。

profile 激活时，主插件按名字取服务（`ContextEngine.GetService(fiber, "standard")` 等），调用它的 `[Service.invoke](配置, 上下文)` 产出实例。四个关键性质：

- **按名发现，缺了等待**。profile 写了不存在的引擎名，profile 停在等待态并报 `missing required service`；插件装好重载后自动装配。这让「先写 profile、后装引擎包」的工作流成立。
- **profile fiber 带内核依赖**。引擎 provider 与扩展都在 profile 的 fiber 里取服务，所以 `ishiki` 也写进了这条 fiber 的依赖表——引擎实现里读 `ctx.ishiki`（如 `gateway`、`logger`）不会触发未声明依赖的警告。
- **会话状态按 runtime 派生**。上下文、唤醒实例各自创建，所以剧情和 v3 唤醒意愿值按频道隔离（channel 模式下）。工具调用包装器与模型在 profile 级共享，不能把当前会话状态放在包装器中。
- **扩展与引擎同机制**。扩展（`ishiki.ext.<名>`）也是同样的 Service 契约，只是贡献面被限定在工具与提示词。

## 三族引擎各自的设计约束

**唤醒引擎负责输入驱动的自动唤醒。** 它在 `attach(agent)` 里订阅 core 的 `message.appended` 通知，从已提交的消息中挑出自己关心的那些，自行判断、自行定时，认定该醒时直接调用 `agent.continue()`。它只管这一类自动响应：模型声明的 `wait` 条件与显式 `wake` 是另外两条独立来路，不经过它。事实流不归它管——runtime 早已把消息写完，引擎只是读者，所以换引擎不改变「收到过什么」，只改变「要不要理」。有状态的需求（v3 的意愿值、jev 的冷却期）在实例内部维护，状态粒度即实例粒度；忙碌时怎么处理（等待、重试、放弃）也由引擎自己定。

**上下文引擎只做投影。** 它在每轮请求前被调用（`prepareEntries`），把事实流投影成模型输入，可以追加系统提示词（如 v3 的 WorldState 说明、记忆块）。它不修改事实流本身——压缩类操作（standard 的摘要）以**追加新条目**的方式表达，历史永远可回放。

**工具调用引擎包装模型的执行方式。** native 直接使用模型原生 function call；v3/hermes/qwen3coder/morph-xml/yaml-xml 处理文本工具协议，让不支持 function call 的模型也能使用工具。`narrative` 则在同一个 `LanguageModelV4` 调用内部协调 Narrator、Action Decoder 与 Replyer，再返回普通 reasoning 与工具调用。真正的工具执行仍由宿主 Agent 完成。

## v3 引擎族：迁移通道

三族里都有 `v3` 变体不是巧合——它们是从 YesImBot v3 迁移的行为：

- `context: v3`：WorldState 视窗（`<working_memory>` 分已处理/新事件）+ 核心记忆块（`memory/*.md` 注入 system）。
- `wakeup: v3`：响应意愿模型（base/atMention/衰减半衰期/回复成本……意愿超阈值按概率开口）。
- `toolcall: v3`：JSON OUTPUT 协议，每步强制输出 `thoughts`（observe/analyze_infer/plan 三段）+ `actions`。

三者可以独立启用——v3 上下文配 native 工具调用完全合法。它们是「老体验」的完整还原，但不再绑定：想混搭新引擎，随意。

## narrative：叙事会话与模型编排

narrative 的两个引擎由 `koishi-plugin-ishiki-narrative` 提供：构建并链接 `packages/narrative`，在 `koishi.yml` 启用 `ishiki-narrative: {}`，profile 里按名字选中即可。插件缺席时 profile 停在等待态，装好重载后自动装配。

ContextEngine 维护的是可恢复的叙事会话，不是另一个常驻 Agent：它把新增事件投影成输入，在已完成步骤的 `turn.step` 订阅中追加剧情条目。包装器没有自己的历史，只从当前输入运行角色阶段。旧剧本保留为稳定前缀，当前原始证据另列，模型输出的剧本不再当新消息重译。

`turn.step` 订阅会被 core 等待，但此时可能已有新消息合入台账。剧本条目因此只认领本次请求带入的源 ID，不能把步骤结束时的整个尾部标成已处理。带标记的 assistant 输出与它的剧情投影通过来源 ID 对齐，恢复时可补投影，无需重做外部动作。配置见[管理上下文窗口](/docs/guides/context)。

## 自己写一个引擎

最小代价的入口是唤醒引擎（一个只订阅、只开轮的实例）：

```ts
import { WakeupEngine, type Agent, type WakeupEngineInstance } from "koishi-plugin-ishiki";
import { Service, type Context } from "koishi";

class MyWakeupInstance implements WakeupEngineInstance {
  attach(agent: Agent): () => void {
    return agent.channel.subscribe("agent", (event) => {
      if (event.type !== "message.appended") return;
      const message = event.message;
      if (message.role !== "custom" || message.type !== "ishiki.message.created") return;
      if (agent.isIdle() && Math.random() < 0.1) agent.continue();
    });
  }
}

export class MyWakeupEngine extends WakeupEngine<"my-wakeup"> {
  constructor(ctx: Context) { super(ctx, "my-wakeup"); }
  public [Service.invoke](config, context) { return new MyWakeupInstance(); }
}
```

`attach` 要做三件事：订阅 `agent` 频道的 `message.appended`、从中挑出关心的消息、判定成立就 `agent.continue()`。两个约束值得记住：订阅回调被 core 等待，耗时的判定（如 jev 的模型调用）要另起任务并自行捕获错误；开轮前要确认 `agent.isIdle()`，异步判定在结果回来后再确认一次——上面例子里判定与检查都是同步的，所以天然安全。

作为 Koishi 插件发布后，用户在 profile 写 `wakeup: { engine: my-wakeup }` 即用。上下文与工具调用引擎同理（基类分别为 `ContextEngine`、`ToolcallEngine`），接口细节见[扩展 API 参考](/docs/reference/api)。

<Callout title="引擎改变行为，扩展增加能力">
如果你在写「给模型加几个工具」，那是扩展；如果你在写「换一种决定历史的方式」，才是引擎。
</Callout>
