`runtimes/<实例 key>/events.jsonl` 是实例记忆的唯一事实源，[数据目录参考](/docs/reference/data-layout)给出它在磁盘上的位置，本页说明它每一行的形状。

条目流格式来自 `@yesimagent/core`，通用层以该包 0.0.9 自带的 `docs/session-storage.md` 为准（落盘布局、追加语义、加载与重建语义、失败模型）。本页只做承接和 Ishiki 特化：说明通用条目在 Ishiki 里什么时候出现，并把 Ishiki 自定义条目与自定义消息逐类列到字段级。

## 条目基类

文件是逐行 JSON，一行一条条目，UTF-8，LF 结尾，只追加不重写。

<TypeTable
  type={{
    id: {
      type: 'string',
      required: true,
      description: '这一行的编号，默认 UUID；与消息自身的 id 不同',
    },
    type: {
      type: 'string',
      required: true,
      description: '条目类别：内建的 event / message / state，或 Ishiki 自定义条目名（如 ishiki.chat.shake）',
    },
    data: {
      type: 'object',
      required: true,
      description: '载荷，形状由 type 决定',
    },
    timestamp: {
      type: 'number',
      required: true,
      description: '落盘时刻，毫秒',
    },
    turnId: {
      type: 'string',
      description: '所属回合；只有调用方传入时才出现，缺省时整个键不写，文件里不会出现 null',
    },
  }}
/>

两个 id 容易混：`entry.id` 是这一行的编号，`data.id`（只有消息有）是消息自身的编号。排查时按哪个字段查要分清，同一个值不会同时出现在两处。

### 三类内建条目

<TypeTable
  type={{
    message: {
      type: 'object',
      required: true,
      description: '一条消息，data 就是消息对象；含 user / system / assistant / tool / custom 五种 role。Ishiki 收到的平台事件与工具产出的图片都以 custom 消息落在这一类里',
    },
    event: {
      type: 'object',
      required: true,
      description: '回合生命周期事件；data 形如 { type, turnId, totalUsage?, error?, reason? }',
    },
    state: {
      type: 'object',
      required: true,
      description: '状态快照，data 为整份状态；Ishiki 没有扩展也没有修改过状态，实例文件里不会出现这一类',
    },
  }}
/>

事件只落盘四种：`turn.start`、`turn.done`、`turn.failed`、`turn.aborted`。`tool.start` / `tool.done` / `tool.failed` / `tool.blocked`、`turn.step`、`turn.queued`、`message.appended`、`agent.init` / `agent.stop` 只经内存与 channel 分发，文件里不会有。`state` 同理：Ishiki 从未调用状态的写入方法，这条路径只在宿主扩展 `AgentCustomState` 后才会产生数据。

写入顺序由运行时决定，Ishiki 一侧的接入点在 `packages/koishi-plugin-ishiki/src/runtime.ts:247-266`：

- 平台消息先经 `deliver` 以 `trigger: false` 送进流；没有进行中的回合时落成不带 `turnId` 的 `message` 条目，有则并入该轮。
- 回合进行中产生的 assistant 与 tool 消息带当前 `turnId`；同批追加的尾部由 `onAppend` 接上 codemode 提交与 `ishiki.images` 记录。
- 准备请求时上下文引擎按预算追加 `ishiki.chat.shake`、`ishiki.chat.compact` 或 `ishiki.compact`。
- narrative 引擎在每个 `turn.step` 之后把带标记的 assistant 输出投影成 `ishiki.narrative`。

## 自定义条目

这类条目自带条目名，`entry.type` 不再是 `message` / `event` / `state`。`ishiki.chat.shake`、`ishiki.chat.compact`、`ishiki.compact` 不带 `turnId`；`ishiki.images`、`ishiki.narrative`、`ishiki.codemode.store` 带。

| 条目名 | 何时写入 | `turnId` | 写入位置 |
| --- | --- | --- | --- |
| `ishiki.chat.shake` | chat 引擎把工具输出折叠成摘要时 | 无 | `packages/koishi-plugin-ishiki/src/context/chat.engine.ts:1392` |
| `ishiki.chat.compact` | chat 引擎把旧历史压成摘要时 | 无 | `packages/koishi-plugin-ishiki/src/context/chat.engine.ts:1524` |
| `ishiki.compact` | standard 引擎压缩上下文时 | 无 | `packages/koishi-plugin-ishiki/src/context/standard.engine.ts:446,460` |
| `ishiki.images` | 一轮请求实际投喂或释放图片后 | 有 | `packages/koishi-plugin-ishiki/src/resource/projection.ts:125` |
| `ishiki.narrative` | narrative 引擎把带标记的 assistant 输出投影成剧本时 | 取自来源消息 | `packages/narrative/src/context/narrative.engine.ts:526` |
| `ishiki.codemode.store` | codemode 脚本写过 store 时 | 有（可缺省） | `packages/koishi-plugin-ishiki/src/builtin-tools/codemode.ts:376` |

### ishiki.chat.shake

上下文超出高水位时，chat 引擎先把工具输出折叠成一段摘要文本，原文写入 artifact。同一块工具内容只折叠一次：投影时遇到该条目的覆盖范围就整段跳过（`chat.engine.ts:287-296`）。字段定义在 `chat.engine.ts:200`。手动入口是 `ishiki.chat.shake` 命令。

      type: 'string',
      required: true,

### ishiki.compact

standard 引擎的压缩只有两个字段，比 chat 引擎朴素：没有 artifact，没有统计，摘要之外只留锚点。字段定义在 `standard.engine.ts:17`。

<TypeTable
  type={{
    summary: {
      type: 'string',
      required: true,
      description: '摘要正文；锚点之前的消息不再进入上下文，改为这段文本',
    },
    lastEntryId: {
      type: 'string',
      required: true,
      description: '被丢弃的最后一条 entry id；读取时找不到该 id 就整段忽略摘要并记一条警告',
    },
  }}
/>

两种写入路径：正常压缩用新生成的摘要（`standard.engine.ts:460`）；裁剪范围内没有消息可摘要时仍追加一条，沿用上一份摘要、只推进锚点（`standard.engine.ts:446`）。

自动压缩在回合结束时触发（`standard.engine.ts:373-380`），前提是上一轮请求已经超预算；手动入口是 `ishiki.standard.compact` 命令。

### ishiki.images

图片投递记录：记录一轮请求里哪些附件被真正送进模型（`shown`）、哪些此后不再送（`released`）。键的格式是 `<附件消息的 data.id>:<items 下标>`。字段定义在 `projection.ts:44-46`。

<TypeTable
  type={{
    shown: {
      type: 'string[]',
      required: true,
      description: '本轮实际投喂给模型的图片槽位',
    },
    released: {
      type: 'string[]',
      required: true,
      description: '本轮起不再投喂的槽位：once 生命周期的图展示一次后释放；模型关闭图片输入、媒体类型或编码不支持、超出数量或字节预算的图直接释放；recent 图超出保留数量后按批释放',
    },
  }}
/>

真实写入的一行（该轮只有一张图；`once` 生命周期的图展示后立即释放，同一下标同时出现在两个列表里）：

```json
{"id":"8f4b0fe9-616a-40c9-9503-71ec3081d2b7","type":"ishiki.images","data":{"shown":["32ea75ba-88a7-4465-be29-57140327a2b7:0"],"released":["32ea75ba-88a7-4465-be29-57140327a2b7:0"]},"timestamp":1793531049958,"turnId":"e061c676-0701-4e5c-b2c8-565cf9462c91"}
```

写入挂在 `onAppend`（`runtime.ts:247-250` → `projection.ts:119-126`）：只有同一批追加里出现了本轮 assistant 消息时才落一条，所以它总是排在那一轮的 assistant 消息之后。重启后 `restore`（`projection.ts:90-118`）用这些历史记录重建槽位，已释放的图不会被重新投喂。

### ishiki.narrative

narrative 引擎不改写原始消息，只把带标记的 assistant 输出投影成同一条台账上的剧本条目。原始消息、工具调用与执行结果仍在原处，条目只是投影。字段定义在 `packages/narrative/src/narrative.ts:17`。

<TypeTable
  type={{
    originMessageId: {
      type: 'string',
      required: true,
      description: '来源 assistant 消息的 data.id',
    },
    script: {
      type: 'string',
      required: true,
      description: '剧本正文，取自该消息带 ishiki.narrative 标记的 reasoning 部分',
    },
    kind: {
      type: '"delta" | "summary"',
      required: true,
      description: '增量段落或摘要段落',
    },
    inputEntryIds: {
      type: 'string[]',
      description: '仅 delta：这段剧本读过的 entry id，已过滤掉来源消息之后的 id',
    },
    next: {
      type: '{ kind: "action" | "stop" | "reply"; target?; mode?; continue? }',
      description: '仅 delta：下一步动作声明',
    },
    throughOriginMessageId: {
      type: 'string',
      description: '仅 summary：摘要覆盖到的最后一条来源消息',
    },
  }}
/>

写入两只手：每步结束后按 `turn.step` 事件补投影（`narrative.engine.ts:287-299`），准备请求时再扫一次补漏（`narrative.engine.ts:306`）。投影是幂等的，同一来源消息的同类条目只写一次。`turnId` 沿用来源 assistant 条目的值。

投影缺失时引擎从带标记的 assistant reasoning 恢复，不会因此重新调用工具。

## 自定义消息

这类条目的 `entry.type` 仍是 `message`，区别在 `data.role` 是 `"custom"`，真正的类别写在 `data.type`。声明位置 `packages/koishi-plugin-ishiki/src/types/messages.ts:4-13`。

判断一行是不是自定义消息用 `role`，判断是哪一类用 `type`，不要拿条目级 `type` 去找它们。

## 核对与排查

以下命令在真实文件上跑过，输出原样粘贴。核对用的样例文件 9 行，由真实 `AgentRuntime` 与 JSONL 存储写出（模型端点为固定响应，平台名为测试用的 `test`）；`ishiki.chat.shake` 与 `ishiki.chat.compact` 的样例行来自另一次维护运行产生的文件。

```
      6 message
```

自定义条目自带类别，message 再看 `role`（自定义消息看 `data.type`）：

```bash
jq -r 'select(.type=="message") | .data.type // .data.role' events.jsonl | sort | uniq -c
```

```
      2 assistant
      1 ishiki.attachment
      2 ishiki.message.created
      1 tool
```

判据：`turn.start` 的数量应等于 `turn.done` + `turn.failed` + `turn.aborted`；不等说明有回合没写完。`ishiki.images` 只在有图投喂或释放的轮次出现，条数不固定。

### 定位非法 JSON 的行号

整文件解析会在第一条坏行处停下，只给出偏移量：

```bash
jq -c . broken.jsonl > /dev/null
```

```
Error: failed to parse: byte offset 1849: colon expected
```

退出码为 5。逐行扫描能直接给出行号：

```bash
awk 'NF { print NR "\t" $0 }' broken.jsonl | while IFS=$'\t' read -r n line; do printf '%s' "$line" | jq -e . >/dev/null 2>&1 || echo "bad line: $n"; done
```

```
bad line: 5
```

修法：删掉坏行的整行即可，其余行不受影响。手工编辑前先停掉对应 Runtime，停实例与归档的操作见[数据目录参考](/docs/reference/data-layout)。

### 常见异常

- 摘要锚点丢失：`ishiki.compact` 的 `lastEntryId` 在文件里找不到时，standard 引擎忽略整段摘要并记警告（`standard.engine.ts:333-337`），表现为压缩后记忆突然变短。
- 图片重复投喂：`ishiki.images` 缺失或被手工删掉，恢复时认不出哪些图已经给过模型，会重新投喂一遍。
- codemode store 不一致：`ishiki.codemode.store` 被删或被重排，重放出来的 store 与脚本当时看到的不同。条目只能追加，重排等于改历史。
