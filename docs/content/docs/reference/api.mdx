本文面向二次开发者：Ishiki 的可编程面由三部分组成——扩展（Extension）、引擎（Context/Wakeup/Toolcall Engine）、资源方案（SchemeHandler）。全部接口由主包 `koishi-plugin-ishiki` 导出（源码：`packages/koishi-plugin-ishiki/src/`）。

## 扩展：贡献工具与提示词

扩展是一个继承 `Extension` 的 Koishi Service，按 profile 的 `extends.<包名>` 被装配。基类契约（`src/extension.ts`）：

```ts
import { Extension, type ExtensionContext, type ExtensionInstance } from "koishi-plugin-ishiki";
import { Service, type Context, type Schema } from "koishi";

export default class MyExt extends Extension<MyConfig> {
  static inject = ["ishiki"];

  // 可选：实例配置的 Schema（来自 profile 的 extends.<名>.config）。
  // 缺省时配置原样透传。注意这不是插件自身的 Koishi 配置。
  public Schema?: Schema<MyConfig>;

  constructor(ctx: Context, config: MyExt.Config) {
    super(ctx, "my-ext");                 // 注册为 ishiki.ext.my-ext 服务
    ctx.ishiki;                            // 主插件服务（dataPath 等）
  }

  // 每个 runtime 实例装配期调用一次；返回 undefined 表示该实例不贡献
  public [Service.invoke](config: MyConfig, context: ExtensionContext): ExtensionInstance {
    return {
      extendInstructions?: () => string | Promise<string>,      // 追加系统提示词
      extendTools?: () => ToolSet | Promise<ToolSet>,            // 追加工具
      attach?: (handle: AgentRuntime) => (() => void) | void | Promise<void>,  // runtime 装配完成后调用一次，返回值作为释放函数
      stop?: () => void | Promise<void>,                         // runtime 停止时清理
    };
  }
}

namespace MyExt {
  export interface Config { logLevel: number }   // 插件自身配置（koishi.yml）
  export const Config: Schema<Config> = /* … */;
}
```

要点与约束：

<Callout title="能贡献的只有工具与提示词">
这是刻意的边界：扩展不改变控制流。要改变「理不理」「看什么」「怎么调」，请写引擎。
</Callout>
- 工具名与内置工具或其它扩展重名会让该 profile 装配失败（`ToolConflictError`）。
- `context.resources.attach(handler)` 注册自定义资源方案；`stop()` 里应 `dispose()` 注销。
- 同一 profile 的所有实例共享你 `[Service.invoke]` 的每次调用产物之间的隔离取决于你自己——每个实例独立调用一次。

### 运行时句柄（AgentRuntime）

`attach(handle)` 在 runtime 装配完成后调用一次，`handle` 是该实例的 `AgentRuntime`——宿主自用的那组原语：

要点：

- `attach` 可以返回一个释放函数；runtime 停止时，释放函数与 `stop()` 都会被调用。
- 扩展的定时器与主动消息走 `wake`；要把外部输入交给事实流则用 `deliver`。
- 日程、防抖这类自动响应策略请注册一个唤醒引擎：它订阅提交通知，按自己的规则决定何时开轮。显式 `wake` 始终可用，不受引擎影响。

### 可复用的工具构造件

从主包导出（`@yesimagent/core` 再导出 AI SDK 全量）：

- `tool({ description, inputSchema, outputSchema, execute, toModelOutput? })`：定义工具；`inputSchema` 用 `jsonSchema<T>()` 声明。
- `jsonSchema`、`ToolSet`、`ToolCallers`（供 codemode 收编的工具路由）。
- 工具返回值最终会过统一输出出口（截断、媒体归档），你不需要（也不应该）在工具内自行截断。

## 引擎：替换三族行为之一

三族引擎（上下文/唤醒/工具调用）都是继承各自基类的 Koishi Service，按名字注册为 `ishiki.engine.<族>.<名字>`：

```ts
import { ContextEngine, type ContextEngineInstance } from "koishi-plugin-ishiki";

export class MyContextEngine extends ContextEngine<"my-engine"> {
  constructor(ctx: Context) {
    super(ctx, "my-engine");
  }

  public [Service.invoke](config, context: ExtensionContext): ContextEngineInstance {
    return new MyContextInstance(config.myEngine, context);
  }
}
```

实例接口（按族）：

把配置写进引擎 map（`declare module` 合并 `ContextEngines` 等）即可获得 profile 配置段的类型支持；用户在 profile 里写 `engine: my-engine` 即可启用。主插件构造时只注册内置引擎；自定义引擎作为普通 Koishi 插件安装，profile 激活时按服务名发现，缺了就停在等待态。

## 运行时：投递事件与唤醒

实例的 `AgentRuntime` 就是扩展 `attach` 收到的那个句柄，它把两个内部原语直接暴露出来：

```ts
handle.deliver(event);      // 投递一个事件（整形好的 IshikiEvent）
handle.wake(prompt?);       // 主动打开一轮
```

- `deliver(event)` 是纯摄取：捕获附件，然后 `agent.send(event, { trigger: false, ifBusy: "join" })`，成功投递后即返回——返回不代表已经落盘。空闲时持久化在后台进行；有轮在跑时消息接入那一轮，在这一步的输出批次之后一起提交。提交完成的信号是 `message.appended` 通知。它不做任何决定，也不自己开轮——要不要开轮由唤醒引擎或显式 `wake` 决定。
- `wake(prompt?)` 等价于 `agent.continue(prompt)`，是绕开唤醒引擎的显式唤醒，供扩展的定时器与主动消息使用。

`agent.continue(prompt?)` 来自 `@yesimagent/core`：空闲时它排入一轮并返回 turn id；带 `prompt` 时该轮以这段文本作为开场的 user 消息（原文写入，不做包装），不带时这一轮直接基于已有历史开始，不写任何占位消息。忙碌或已有待发唤醒时，请求并入唯一那个待发唤醒并返回 `undefined`，待队列排空即触发——即使上一轮以终态收尾也会补上；此时多次 `continue` 的 `prompt` 以 `; ` 连接进同一条消息。

## 资源方案：让 read 认识你的 URL

实现 `SchemeHandler` 并用 `context.resources.attach(handler)` 注册。中心只按 scheme 路由，handler 收到完整 URL，自行解释路径、query、view 或嵌套 URI。例如 `clock://now` 返回当前时间：

```ts
import { ResourceError, type ResourcePayload, type SchemeHandler } from "koishi-plugin-ishiki";

export class ClockHandler implements SchemeHandler {
  readonly scheme = "clock";

  resolve(input: string): ResourcePayload {
    const url = new URL(input);
    if (url.hostname !== "now") {
      throw new ResourceError("resource_not_found", "expected clock://now");
    }
    const text = new Date().toISOString();
    return { type: "text", url: input, text, size: Buffer.byteLength(text) };
  }
}
```

`ResourcePayload` 分成文本 `{ type:'text', url, text, size, mediaType?, filename?, source? }` 与媒体 `{ type:'file', url, bytes, mediaType, size, filename?, immutable }`。媒体的 `immutable: true` 只用于已固定内容的引用；动态来源使用 false，作为历史附件时由统一出口固化快照。

普通 handler 无需提供续读协议：返回的文本在模型出口超预算时完整固化为 artifact，再从 artifact 分页。codemode 内 read 仍取得完整原始内容。

文件型 scheme 继承 `FileScheme`，声明 scheme 并实现受保护的 `open(url: FileUrl)`。返回的 `FileEntry` 指明文件路径、可选 filesystem、媒体类型和元数据。未提供 filesystem 时使用宿主文件系统；提供实际沙箱的 `ResourceFileSystem` 时，读取同一个虚拟文件视图。`readFileBuffer`、`stat`、`readdir` 是必需能力，流式文本读取为可选优化。

FileScheme 复用行选择、元数据视图与无损 offset 续读。其读取来源随结构化结果传递，不依赖闭包或跨调用缓存。根目录和符号链接约束由具体 scheme 的 open 实现负责；不能把宿主路径当作虚拟路径。

约束：

- `asset` / `artifact` / `local` 是保留方案，注册同名 handler 会被拒绝；注册返回的 disposer 用于注销。
- 使用 `ResourceError` 表达资源错误，例如 `invalid_resource_uri`、`resource_not_found`、`resource_too_large`、`unsupported_view`。
- scheme 注册和存储按 Runtime 隔离；工具只有明确实现了资源中心读取，才能把该 scheme URL 作为数据来源。

## 事件与消息类型

`IshikiEvent`（`src/types.ts`）是实例收到的输入：`ishiki.message.created` / `ishiki.message.deleted` / `ishiki.attachment` / `ishiki.tools.catalog`，字段见源码。它是 core `AgentCustomMessage` 声明的联合：要加自己的事件类型，用 `declare module "@yesimagent/core"` 把类型并进 `AgentCustomMessage`，再用 `createCustomMessage` 构造，`deliver` 与 `message.appended` 的窄化就都认识它。核心不识别具体平台事件——平台事件由会话处理器整形成 `ishiki.message.created` 才进入事实流。

扩展一般不直接消费事件——唤醒引擎与上下文引擎才是它们的第一读者。入站事件先写进事实流，`message.appended` 通知随后到达每条订阅；同一批通知里还混着工具目录、附件与模型输出，所以谁关心什么由订阅方自己过滤。

## 版本与兼容提示

- 全部接口随 0.0.x 演进，**以主包导出的 TypeScript 类型为准**；本文描述与类型冲突时以类型为准。
- 主包 re-export `@yesimagent/core`（Agent 运行时）与 `@yesimagent/gateway`（模型网关），扩展可直接 import 主包而不必声明这两个依赖。
- 装配失败（服务缺失、工具重名、配置校验不过）一律表现为 profile 停在等待态或被跳过，开发期把 `logLevel` 开到 3 定位。
