---

唤醒不是「每条消息都过一道闸」：任何一次醒来都由三个来源之一打开——模型自己声明的等待条件、唤醒引擎的机械信号、扩展或宿主安排的外部唤醒。唤醒引擎只负责第二类，在事件落盘之后回答一次「这条消息要不要理」。

本文先讲这三条来路与模型侧的 `wait` 工具，再给出三种内置引擎的配置方法。

配置位置：profile 的 `wait` 段（默认等待条件）与 `wakeup` 段（引擎）。缺省引擎为 `standard`。换引擎只改 `engine` 字段，其余段与上下文、工具调用引擎互相独立、可任意混搭。

## 醒来有三个来源

1. **模型自己声明的等待条件**。上一轮里模型已经说明「等 N 条新消息」或「等 T 秒」，条件满足即醒来。这是「等他说完再回应」的表达方式。
2. **唤醒引擎的机械信号**。每个入站事件（`ishiki.message.created` / `ishiki.message.deleted`）在**写入事实流之后**恰好交给唤醒引擎判定一次；判定为 `trigger` 就打开一轮。下面「三种引擎」一节里的三种引擎都属于这一类。
3. **外部唤醒**。扩展或宿主主动要求醒来（`runtime.wake(reason?)`、`ctx.ishiki.wake(address, reason?)`），例如扩展自己的定时器或主动消息。

三者互相独立，任一满足就醒来。消息在到达时就已写入事实流，所以「没被唤醒」不等于「没收到」——它只是保持沉默，等下一次醒来时一起看。

## 声明等待：wait 工具

`wait` 是常驻工具，只能在模型目录里直调（不进 codemode 沙箱，也不受 `direct` 名单影响）。它是模型在某一轮里说的一句话：「下一轮什么时候叫我」：

```ts
wait({ msgs: 3, secs: 60 })
```

<TypeTable
  type={{
    msgs: {
      type: 'number',
      description: '再积累 N 条新入站消息后醒来',
    },
    secs: {
      type: 'number',
      description: 'T 秒后醒来，与有无输入无关（≥1）',
    },
  }}
/>

两者谁先到谁生效。语义要点：

- **一次性声明，不是定时触发器**。一次声明触发一次即作废，没有周期、没有配置兜底、不写事实流。runtime 重启后没有待触发的条件，安静地等下一条输入或下一次外部唤醒。
- **它是收尾动作**。和 `finish`、`send_message` 一样，调用它就结束当前轮次。两种自然写法都成立：说完话的同一步里顺手声明，或者不说话只声明。声明不必等到「轮次要结束的时候」——那一刻并不存在。
- 一轮里以最后一次调用为准，条件在轮次结束时生效。
- 不调用它，就等于「不叫醒我」：之后只有机械信号（被点名、被引用、私聊）与外部唤醒能打开下一轮。没有 profile 默认值可以兜底——这条节奏完全交给模型当轮判断。
- 返回值回显真正生效的窗口；空调用返回 `none: true`，明确告诉模型这一轮之后没有排定唤醒。

### 怎么选

默认的行为指引只给几条：先看上下文和未回应的输入；对方可能还在打字就稍等一拍；话题不属于自己就保持沉默；被点了名但没内容，不等于必须立刻回话。

落到 `wait` 上：

| 场景 | 声明 |
| --- | --- |
| 一句话可能还没说完、@ 了但没内容 | `{msgs: 1, secs: T}` — T 在群聊里取短些，私聊里长些 |
| 话题与自己无关 | 不调用 — 让被点名这件事把自己带回来 |
| 正常对话，说完了 | `{msgs: 1, secs: T}` 等着对方接话，或不声明 |

「每一条输入最终都会得到回应」不是这里的保证。保证更窄：输入保持待回应状态，每次醒来都会被重新考虑；但没有排定唤醒时的沉默，是合法的结果。

## 唤醒引擎在什么时候被调用

runtime 只把入站事件交给引擎一次，且一定在事件落盘之后：

- `runtime.deliver(event)` 是纯摄取：捕获附件、立即把事件记进事实流（`trigger: false`、`ifBusy: "join"`）、给生效中的消息窗口计数。它不做任何决定，也不攒着消息——消息在到达时就是耐久的。
- 落盘后，runtime 订阅 `message.appended`，过滤出 `ishiki.message.created` / `ishiki.message.deleted`，对每个入站事件调用一次 `wakeup.decide(event)`；判定为 `trigger` 时执行 `agent.continue("signal")`，把唤醒原因带进新的一轮。

（jev 与 v3 引擎的内部判定保持原样，接入方式对它们透明。）

## 三种引擎的常用配置

按场景对号入座，下面给出三种引擎最常被采用的配置形态。

<Tabs groupId="wakeup-engine" items={['standard｜关键词触发', 'v3｜响应意愿', 'jev｜模型判定']}>
<Tab value="standard｜关键词触发">

### 固定规则，零额外开销

standard 引擎按固定规则判定，不消耗额外模型调用：

```yaml
wakeup:
  engine: standard
  standard:
    direct: true          # 私聊必醒
    atSelf: true          # 被 @ 必醒
    quoteSelf: true       # 引用回复 bot 的消息必醒
    keywords:             # 消息包含任一关键词必醒
      - neko
      - 喵酱
```

四条规则独立生效，命中任一即唤醒。全部关掉（四项全 false/空）后引擎不再主动开轮，消息仍会进入事实流；此时自动唤醒还在生效，要让 bot 真正「只听不说」，还需要把 `wait` 两维都设为 0（并且模型不再自行声明条件）。

默认值：`direct`、`atSelf`、`quoteSelf` 均为 `true`，`keywords` 为空。

</Tab>
<Tab value="v3｜响应意愿">

### 意愿值：多数时候沉默，偶尔自然插话

v3 引擎为每个频道维护一个「意愿值」：被 @ 、私聊等事件加分，被打扰后衰减，意愿越高越可能开口。适合「多数时间沉默、偶尔自然插话」的群聊人格：

```yaml
wakeup:
  engine: v3
  v3:
    base: 12                      # 一条普通消息的基础分
    atMention: 100                # 被 @ 的加成
    isQuote: 15                   # 引用 bot 消息的加成
    isDirectMessage: 40           # 私聊的加成
    keywords: [neko, 喵酱]        # 命中任一即改用 keywordMultiplier
    keywordMultiplier: 1.2
    defaultMultiplier: 1
    maxWillingness: 100           # 意愿上限
    decayHalfLifeSeconds: 600     # 无打扰时的衰减半衰期（秒）
    probabilityThreshold: 55      # 意愿超过此值才有概率开口
    probabilityAmplifier: 0.04    # 超出阈值部分换算成开口概率的系数
    replyCost: 35                 # 每开口一轮扣掉的意愿
```

调节思路：

- **太话痨** → 调高 `probabilityThreshold` 或 `replyCost`；调低 `base`。
- **太沉默** → 反向调节，或调低 `decayHalfLifeSeconds` 让热情维持更久。
- `keywords` 命中不是「必醒」，而是乘上 `keywordMultiplier`，所以话题相关时更容易被唤醒。

channel 模式下每个频道独立计分，群聊和私聊天然分开，不需要拆 profile。

</Tab>
<Tab value="jev｜模型判定">

### 让模型自己判断此刻该不该开口

jev 引擎把「要不要说话」交给一次轻量模型调用。它按三个维度各问一句——是不是在跟 bot 说话（addressed）、bot 对这个话题有没有话说（interested）、是不是别人之间的对话（others）——合成为 0 到 1 的量，超过阈值才开口：

```yaml
wakeup:
  engine: jev
  jev:
    apiKey: ${TYPESAFE_API_KEY}   # 或环境变量 TYPESAFE_API_KEY
    model: jev-latest             # 判定模型，走 typesafe-ai 方言
    threshold: 0.5                # 合成量的开口下限
    cooldownMs: 30000             # 上次开口后的静默期（毫秒）
    historyMessages: 8            # 每次判定喂给模型的最近消息条数
    timeoutMs: 1500               # 判定超时（毫秒），超时按不唤醒处理
    instruction: |                # 判定的补充约束（语气、何时闭嘴）
      neko，猫娘，话不多但会接梗。
      只在有人点名、话题与自己在做的工作有关、或有人明显在征求意见时插话；
      几个人互相寒暄时保持安静。
    interests:                    # 「感兴趣的话题」，只影响 interested 维度
      - LLM 工程与调试
      - TypeScript
    rules:                        # 兜底规则：命中即醒，不问模型
      direct: true
      atSelf: true
      quoteSelf: false
      keywords: []
```

要点：

- `threshold: 0.5` 是「毫无证据也开口」的临界值——三个维度都给 0.5 时合成恰好 0.5。调高它收紧的是合成量。
- `interests` 决定「bot 对什么话题有话说」，是 interested 维度唯一的信息来源；留空则该维度不偏袒任何话题。
- 兜底 `rules` 的结构就是 standard 引擎那四项，只写在 `jev` 段内部。

<Callout type="warn" title="前置条件">
需要 `apiKey`（或环境变量 `TYPESAFE_API_KEY`），且 `models.yaml` 中存在可用的 `typesafe-ai` 方言 provider。两者缺其一时，这份 profile 会在装载时被跳过。
</Callout>

<Callout type="warn">
每条未兜底命中的消息都会产生一次判定调用，高频群会带来持续的 API 消耗与延迟（默认上限 1.5 秒）。
</Callout>

</Tab>

## 验证与排错

换引擎后重启生效。验证 standard/jev 的兜底规则：私聊发一条消息应立即唤醒。验证 v3：连续普通消息后观察意愿爬升（开启 debug 日志可见）。验证 `wait`：让模型在某一轮声明 `wait({ secs: 5 })`，之后不再说话，5 秒后应看到它以一条带原因的 `Continue.` 消息醒来。条件在重启后会恢复：未到期的计时器按剩余时间重新计时，已过期的立即触发一次。

常见问题：

- **profile 被跳过，日志 `wakeup engine "jev" needs an apiKey`** → 补密钥或环境变量。
- **jev 判定永远不醒** → 检查 `timeoutMs` 是否过短、判定模型接口是否可用；`threshold` 是否设得过高。
- **rules 写成 `jev` 的同级段不生效** → 兜底规则必须在 `jev:` 段内部。
- **消息进来却迟迟没有回应** → 这是等待条件在起作用：消息已入事实流，但要等够 `wait` 声明的条数或秒数。看 debug 日志里的条件状态，或把 `wait.msgs` / `wait.secs` 调小。
- **它再也不自动醒来了** → 上一轮可能声明了 `wait({ msgs: 0 })`，或 profile 的 `wait` 两维都是 0；机械信号与外部唤醒仍然有效，也可以在下一轮让它重新声明。
- **它几乎从不用 `wait`** → 提示词里「何时声明」没讲清，或模型被要求等到「轮末」才声明——那一刻并不存在，声明本身就是收尾动作。检查 persona 是否覆盖了默认行为指引；也可以让 `wait()` 不带参数先跑一轮，从回显里看默认条件是否合理。
