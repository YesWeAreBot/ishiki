唤醒引擎决定 runtime 在什么时候开始一轮。输入提交与开启轮次是两条路径：消息到达只负责写入事实流，是否因此开启轮次由引擎判断；接口也允许引擎自己计时，在没有新输入时按计划运行。

profile 的 `wakeup` 段选择变体并给出参数，缺省为 `standard`。

## 醒来由谁触发

1. **模型声明的等待条件**。上一轮用 `wait` 声明「再等 N 条新入站事件」或「等 T 秒」，条件满足即开启轮次。
2. **唤醒引擎**。引擎在 `attach(agent)` 之后自行决定运行时机。内置变体都在消息提交后判定；自定义引擎可以按时钟、外部日程或其他信号开启轮次。
3. **外部唤醒**。扩展或持有 runtime 的宿主代码调用 `runtime.wake(prompt?)`，例如一次性的提醒或主动消息。

三者各自计时、各自触发，任一满足就醒来。入站消息总会写入事实流（提交完成以 `message.appended` 为准），没有触发只表示没有开始新一轮；消息保存在事实日志中，等下一次醒来一并处理。

## 声明等待：wait 工具

`wait` 是常驻工具，由模型直调。它不进入 codemode 沙箱，也不受 `direct` 名单影响。模型在某一轮里用它声明下一次自动唤醒的窗口：

```ts
wait({ msgs: 3, secs: 60 })
```

<TypeTable
  type={{
    msgs: {
      type: 'number',
      description: '再积累 N 条新入站事件（消息创建或撤回）后醒来，0 到 1000；0 表示不按条数排定',
    },
    secs: {
      type: 'number',
      description: 'T 秒后醒来，与有无输入无关，1 到 86400',
    },
  }}
/>

`msgs` 与 `secs` 可以同时给出，先到者生效。语义：

- **一次性声明**。触发一次即作废，没有周期，也不写事实流。runtime 重启后不会恢复未触发的声明。
- **收尾动作**。调用它的那一步结束后本轮不再继续，条件在轮末生效。一轮里多次调用以最后一次为准；`secs` 的计时从条件生效时开始。
- **只在以 `done` 收尾的轮次生效**。轮次以 failed 或 aborted 结束时，声明被丢弃。
- **计数来自提交**。轮内到达的消息已经进入本轮上下文，不会继续计入新窗口；如果声明时这批消息已经达到 `msgs`，条件会在轮末立即触发，使已达到条件的输入及时进入下一轮。
- **不调用等同于不排定唤醒**。之后能开启轮次的只有唤醒引擎与外部唤醒，没有 profile 默认值兜底。
- **返回值回显真正生效的窗口**。没有有效窗口（空调用或 `{msgs: 0}`）时返回 `none: true`，明确告诉模型这一轮之后没有排定自动唤醒。

### 怎么选

默认的行为指引给了几条建议：先看上下文和未回应的输入；对方可能还在打字就稍等一拍；话题不属于自己就保持沉默；被点了名但没内容，也可以继续等。

落到 `wait` 上：

| 场景 | 声明 |
| --- | --- |
| 一句话可能还没说完、@ 了但没内容 | `{msgs: 1, secs: T}`，T 在群聊里取短些，私聊里长些 |
| 话题与自己无关 | 不调用，让被点名这件事把自己带回来 |
| 正常对话，说完了 | `{msgs: 1, secs: T}` 等着对方接话，或不声明 |

输入保持待回应状态，每次醒来都会被重新考虑。没有排定唤醒时保持沉默，是合法结果。

## 唤醒引擎收到的输入

runtime 负责把入站事件写进事实流，引擎在提交之后观察它们。

- `runtime.deliver(event)` 是纯摄取：捕获附件，然后 `agent.send(event, { trigger: false, ifBusy: "join" })`，成功投递后返回。有轮次正在运行时消息接入当前轮，在该步输出之后提交；空闲时持久化在后台进行。返回不代表已经落盘，提交完成以 `message.appended` 为准。
- 提交后，core 在 `message.appended` 上通知订阅者。内置变体在 `attach(agent)` 里订阅这条通知，自行过滤：同一批通知里还混着工具目录、附件与模型输出。
- 引擎认定该开启轮次时调用 `agent.continue()`。自动唤醒不传文本时，模型看到的是已有历史。
- 订阅回调会被 core 等待。长耗时的判定要另起任务并捕获错误，不能堵在提交路径上。
- 开启轮次前检查 `agent.isIdle()`，延迟或异步判定返回后再检查一次。忙碌时等待、重试还是跳过，由引擎自己的策略决定。

`wait` 条件与 `runtime.wake(prompt?)` 是另外两条独立来路，它们直接调用 core 的 `continue`，不经过唤醒引擎，引擎的规则也无法拦下它们。

## 三种内置变体

以下三种变体在消息提交后判定，适合配置消息驱动的触发策略。

<Tabs groupId="wakeup-engine" items={['standard｜固定规则', 'willingness｜响应意愿', 'jev｜模型判定']}>
<Tab value="standard｜固定规则">

### 按固定规则判定，不额外调用模型

standard 引擎按四条规则判定：

```yaml
wakeup:
  engine: standard
  standard:
    direct: true          # 私聊必醒
    atSelf: true          # 被 @ 必醒
    quoteSelf: true       # 引用回复 bot 的消息必醒
    keywords:             # 消息包含任一关键词必醒
      - neko
      - 喵酱
```

四条规则独立生效，命中任一即唤醒。三个开关都设为 false、`keywords` 留空后，引擎不再主动开启轮次，消息仍会进入事实流；此时能开启轮次的只剩 `wait` 条件与外部唤醒。

默认值：`direct`、`atSelf`、`quoteSelf` 均为 `true`，`keywords` 为空。

</Tab>
<Tab value="willingness｜响应意愿">

### 意愿值：多数时候沉默，偶尔自然插话

willingness 引擎按完整频道地址维护「意愿值」：平台、机器人账号与频道三者任一不同，分数就彼此独立。被 @、被引用、私聊、普通消息与图片分别加分，命中关注词再乘系数；分数越高，继续加分的幅度越小。意愿随时间衰减，确认消息发送成功后扣掉 `replyCost`，超过阈值后按概率开口。

```yaml
wakeup:
  engine: willingness
  willingness:
    base: 12                      # 一条普通消息的基础分
    atMention: 100                # 被 @ 的加成
    isQuote: 15                   # 引用 bot 消息的加成
    isDirectMessage: 40           # 私聊的加成
    imageGain: 8                  # 包含图片的加成
    keywords: [neko, 喵酱]        # 命中任一即乘 keywordMultiplier
    keywordMultiplier: 1.2
    defaultMultiplier: 1
    maxWillingness: 100           # 意愿上限
    initialWillingness: 0         # 频道首次出现时的起始意愿
    decayHalfLifeSeconds: 600     # 衰减尺度（秒），数值越大衰减越慢
    hotWindowSeconds: 15          # 最近对话窗口（秒）
    warmWindowSeconds: 60         # 温对话窗口（秒）
    hotDecayWeight: 0.3           # 热窗口内每秒衰减折算的权重
    warmDecayWeight: 0.7          # 温窗口内每秒衰减折算的权重
    probabilityThreshold: 55      # 意愿超过此值才有概率开口
    probabilityAmplifier: 0.04    # 超出阈值部分换算成开口概率的系数
    replyCost: 35                 # 成功发送消息后扣掉的意愿
    atMentionForce: false         # 被 @ 时跳过概率直接唤醒
    quoteForce: false             # 被引用时跳过概率直接唤醒
    directForce: false            # 收到私聊时跳过概率直接唤醒
    participationWindowSeconds: 60 # 回复后参与加成保留的秒数
    participationInfluence: 0.5   # 参与窗口内最高的额外加成比例
```

调节思路：

- **太话痨**：调高 `probabilityThreshold` 或 `replyCost`，或调低 `base`。
- **太沉默**：反向调节，或调高 `decayHalfLifeSeconds` 让意愿保留更久。
- `keywords` 命中会把本轮加分乘以 `keywordMultiplier`，话题相关时更容易被唤醒。
- `atMentionForce`、`quoteForce`、`directForce` 分别让对应情形跳过概率判断；引擎仍会在 Agent 空闲时才开启轮次。

图片加成来自平台附件事件，并与同一条入站消息的 `messageId` 关联；文本中的媒体标记不参与判定。成功发送的确认来自 `send_message` 的返回结果。脚本内调用 `send_message` 时，codemode 外层只暴露调用名称与完成状态，无法看到脚本内部的失败返回值，此时按调用完成扣费。

channel 模式下每个 runtime 只对应一个频道；cross 模式下各频道的分数独立累计，任一条消息所属的完整地址过线时，按概率打开共享 runtime 的一轮。成功回复后，同一参与者、私聊或被点名的消息会在一段时间内获得参与加成；明确 @ 或引用其他人的消息不享受这项加成。

</Tab>

### 让模型判断此刻是否值得开口

jev 会先合并短时间内收到的消息。多位作者同时说话时，它挑出当下最值得回应的那一位，再让决策模型读懂这段对话：话在对谁说，是否在接 bot 刚说过的话，句子是否完整，气氛是否开放，有没有信息或社交价值，话题是否已经结束或撤回。

模型给出判断，发言节奏仍由本地参数控制。`threshold` 与 `addressedThreshold` 决定需要多少证据，冷却时间、连续回复上限和参与比例防止它反复接话，合并等待与上下文预算则决定一次判断能看到多少内容。完整字段见[插件配置参考](/docs/reference/plugin-config#wakeup)。

在 `models.yaml` 中声明决策模型：

```yaml
providers:
  typesafe:
    api: typesafe-ai
    apiKey: ${TYPESAFE_API_KEY}
    models:
      - id: jev-latest
        type: decision
```

profile 引用这个条目。密钥和地址留在 `models.yaml`，`instruction` 用来描述它在群里的表达方式：

```yaml
wakeup:
  engine: jev
  jev:
    model: typesafe:jev-latest     # models.yaml 中的决策模型引用
    threshold: 0.7                 # 主动加入时的贡献门槛
    addressedThreshold: 0.7        # 定向消息的地址证据门槛
    cooldownMs: 30000              # 主动加入的冷却时间（毫秒）
    minIntervalMs: 2000            # 连续主动判定之间的最小间隔
    debounceMs: 800                # 同批消息的合并等待时间
    maxWaitMs: 2500                # 首批消息等待合并的最长时间
    conversationMs: 120000         # bot 发言后的对话延续窗口
    contextMaxAgeMs: 900000        # 判定可读取的历史消息最大年龄
    decisionMaxAgeMs: 10000        # 消息与判定结果允许等待的最长时间
    participationWindowMs: 300000  # 参与比例统计窗口
    maxParticipation: 0.25         # 窗口内主动发言允许占比
    minParticipationTurns: 6       # 参与比例开始生效的消息数量
    maxConsecutiveReplies: 4       # 连续定向回复次数上限
    timeoutMs: 3000                # 单次决策调用超时（毫秒）
    historyMessages: 16            # 判定上下文中的最近消息数量
    contextChars: 3000             # 判定上下文的最大字符数
    instruction: |                 # 人格与发言约束
      你是 Neko，话不多但会接梗。
      只在有人点名、话题与自己在做的工作有关、或有人明显在征求意见时插话；
      几个人互相寒暄时保持安静。
    interests:
      - LLM 工程与调试
      - TypeScript
    rules:                         # 命中后直接唤醒，不调用模型
      direct: true
      atSelf: true
      quoteSelf: false
      keywords: []
```

`interests` 帮模型判断话题是否贴近它关心的事情。`rules` 里的消息会跳过模型直接唤醒，默认只打开私聊与提及。没有命中规则时，消息会短暂合并，再等 Agent 空闲后进入判断。模型引用无法解析时，创建 runtime 会直接报错。

</Tab>

## 自主调度

需要按日程或固定间隔自主运行时，可以编写唤醒引擎：在 `attach` 里维护计时器或读取外部日程，到点检查 `agent.isIdle()` 后调用 `agent.continue()`。完整示例见[引擎系统：写一个自主调度的唤醒引擎](/docs/explanations/engines#写一个自主调度的唤醒引擎)。

runtime 按需创建，计时器从引擎的 `attach` 开始。当前平台接入在首次输入路由到该频道时创建实例。扩展也可以在自己的定时器里调用 `runtime.wake()`，适合一次性的提醒或主动消息；未提供原因或原因只含空白时，运行时写入 `Continue.` 作为开场内容。作为 profile 的长期运行节奏时，写成唤醒引擎更容易替换与配置。

## 验证与排错

修改 profile 后重启插件生效。验证 standard：空闲时发一条私聊消息应立即唤醒。验证 jev 的兜底规则：空闲时，命中 `rules` 的私聊消息应直接开启轮次。验证 jev 的模型判定：关闭 `rules.direct` 与 `rules.atSelf`，发送一条完整、明确的请求，观察 debug 日志中的 `JEV wakes`、`JEV waits` 与模型调用。验证 willingness：连续普通消息后再 @ 一次，观察是否开口；willingness 不输出引擎日志，可以临时打开 `atMentionForce`，或调低 `probabilityThreshold` 观察触发情况。验证 `wait`：让模型声明 `wait({ secs: 5 })`，之后不再说话，5 秒后应看到它自己开了一轮；debug 日志会出现 `wake: timer 5s expired`。等待条件只活在内存里，重启后不会恢复。

常见问题：

- **创建 runtime 时提示模型不存在或类型错误**：检查 `models.yaml` 是否存在 `wakeup.jev.model` 指向的条目，并把模型声明为 `type: decision`。
- **jev 判定永远不醒**：检查 `timeoutMs` 是否过短、模型接口是否可达、`threshold` 与 `addressedThreshold` 是否过高；冷却期、连续回复预算与参与比例也会让引擎保持安静。
- **rules 写成 `jev` 的同级段不生效**：兜底规则必须写在 `jev:` 段内部。
- **消息进来却迟迟没有回应**：可能还在 `wait` 声明的窗口里，也可能被引擎的冷却期或概率跳过。消息已在事实流中，下一次醒来会一并处理。
- **它再也不自动醒来了**：上一轮可能没有排定 `wait`，或轮次以失败结束导致声明被丢弃；引擎规则、冷却期与外部唤醒仍按各自条件生效。
- **它几乎从不用 `wait`**：行为指引没有讲清何时声明，或提示词要求等到「轮末」才声明。检查 persona 是否覆盖了默认指引；也可以让模型调用一次不带参数的 `wait()`，回显会直接说明这一轮之后没有排定唤醒。
- **想让它按时间自主运行**：内置变体不含定时调度，写一个自定义唤醒引擎，见上文「自主调度」。
